### 1.5 Activity-typed grade encoding (interim convention)

`Grade` is unique per (student, assignment, period) with no activity column,
so a migration-free convention is used: an activity selector (Classwork,
Paperwork, Quiz, Recitation, Term exam, Project, Performance task) on the
encode form and edit dialog, stored as a `"[Type] rest"` prefix on `remarks`
(≤255 chars). `parseActivityRemarks` reverses it; unprefixed remarks report
no activity. The grade table shows an Activity chip. A dedicated
grade-activity model is the documented follow-up, not invented here.

### Regressions the browser caught (both fixed)

1. **Public landing page crashed on live CMS data.** `usePublicAnnouncements`
   read `response.data` — a DRF `ListAPIView` envelope
   (`{count, next, previous, results}`) — and `LandingPage` called
   `items.map(...)` over that object, so the page rendered
   `Unexpected Application Error! items.map is not a function`. With Strapi
   down the 502 took the error branch and hid it, so only a live-content run
   could catch this. Both hooks now read through `fetchAllPages`.
   Regression test: `src/features/cms/public-api.test.tsx`.
2. **The authenticated admin CMS hooks had the same defect.** They also read
   the raw envelope, so the "N announcements currently visible to you" count
   and the tables were reading an object rather than rows. Both now use
   `fetchAllPages`.

Two smaller observations, both fixed:

3. **CMS reads retried by default.** the client's single retry doubled the
   wait before a dead Strapi was reported (≈12 s), because each attempt takes
   2–4 s to refuse on this host. All four CMS queries now set `retry: false`
   and the failure lands in ≈8 s.
4. **`/` could not reach the landing page.** The unauthenticated pathless
   route previously lived under `path: "/"`, so the redirect guard claimed
   `/` and bounced visitors to `/login`. The boundary is now pathless and
   matches only `/app…`.

Confirmed against a live mock CMS that the role/expiry filters behave
exactly as specified: anonymous sees 1 (public + unexpired), student sees 1,
admin sees 2 (public + expired, as staff), public resources show only the
all-audience active item.

## 2c. Round 2 — the reviewer's re-check

The first round added new entry points without retiring the old ones. Four
findings, all fixed.

**Duplicated sidebar entries.** Every role's sidebar still carried
`Account → Account Settings` and `Communication → Notifications` after the
header had taken both over, so the same destination sat two places apart on
all five roles. Both groups are gone from every tree
(`navigation.ts`). The routes are untouched — the bell still opens
`/app/notifications` and the account menu still opens
`/app/account-settings`, and `getPageTitle` still titles both pages because
it reads items rather than trees. `ACCOUNT_SETTINGS` and `NOTIFICATIONS`
stay declared for exactly that reason.

**A "Profile" item that pointed at Notifications.** The account menu's
Profile entry linked to `/app/notifications`, which is not what its label
says. The app has no self-profile page — the account surface is the
self-scoped `GET/PATCH /accounts/me/`, which the Settings entry opens — so
the item advertised a destination that does not exist. Removed.

**The assistant followed the reader between pages.** `chatOpen` lived above
the outlet, so the panel survived a route change and stayed open across every
navigation. It now resets on the pathname change, alongside the mobile
drawer. No conversation is lost: the transcript is component state and was
already discarded on close. Covered by a new test in `AppShell.test.tsx`
(open, navigate, assert the panel is gone).

**The Academic Progress subject rows.** Each subject printed its score and
then repeated the same number as a six-pixel bar underneath, which read as an
unfinished rule rather than a chart — the reviewer called it "a straight line
thingy". The bars are gone from the student and parent dashboards. The one
thing the number does not say on its own is now a word: a `Passing` /
`Below passing` / `Not recorded` chip (`lib/score-status.ts`). The threshold
is 75, the school's existing passing mark, restated from
`ai_engine.config.PASSING_GRADE` and the analytics default — not a scale
invented here. This also stops the meaning resting on colour alone, which the
colour-only tier above it was approaching.

Checks: typecheck, lint, format:check, build all pass; `npm test` 737/737
across 51 files (+7: five `score-status` cases, the sidebar-duplication case,
and the assistant case).

## 2d. Round 3 — the last hairline bars, now real charts

The reviewer's pass left three places drawing a "chart" as a six-pixel filled
div, plus one screen that presented the same payload twice. All four were
decided together: donut with counts for guidance, yes to dropping admin's
duplicate, stacked columns for attendance.

**Guidance — `RiskLevelBars` → `RiskLevelDonut`.** The Risk Alerts card now
opens with a donut and, beside it, the exact per-level counts and shares
(`High 2 · 67%`). The donut carries the proportion; the list carries the
numbers, so nothing depends on judging an arc and no figure is hover-only. It
is fed from the alerts already on screen rather than
`useRiskDistribution()`, because those measure different things: this is
*alerts* by level, while `/analytics/risk-distribution/` counts *students* by
computed risk and feeds the administrator donut. Same colour tokens
(destructive / chart-4 / chart-2) so a colour means the same severity in both
places.

**Faculty — `PendingGradesBars` → `PendingGradesChart`.** Two categories do
not warrant a donut, so this is the bar treatment: an axis starting at zero,
a count printed above each column, and the same two totals still written on
the Pending Grades tile. The old rows measured both numbers as a share of one
combined total, which drew "3 drafts and 12 submissions" as a 20/80 split of
a single quantity.

**Attendance — per-section hairlines → `SectionAttendanceChart`.** One
stacked present/late/absent chart for all sections, using the same three
series and colours as the administrator's `AttendanceTrendChart`, with a DOM
legend naming the three so colour is never the only signal. The old rows
restated, as a length, the rate the line above them already printed. The rate
itself is now a `Rate` column in the summary table — it is the figure the card
is named for, and it had lived only above a bar that repeated it. Nothing is
hover-only: the plot's accessible label carries every count and the computed
rate, and the table keeps all four counts.

**Admin — the duplicate risk card removed.** The three-number "Risk
Distribution" card read the same `/analytics/risk-distribution/` response as
the donut rendered below it, twice on one screen, with the hand-rolled version
carrying neither the `insufficient_data` bucket nor the states the chart
handles. The card is deleted; `RiskDistributionChart` keeps all four buckets,
the scored-student footer, and the "engine has not produced scores yet" empty
state that the card's hand-written zero caveat used to carry.

All four charts follow the existing rules: `isAnimationActive={false}`,
`ChartFrame role="img"` labels built from the real data, tokens from
`chart-config`, no new dependency.

**Coverage added** (5 cases): admin keeps one risk presentation (donut, no
three-number card); guidance labels the donut with the per-level counts and
splits a mixed set into counts + shares (2 cases); faculty labels the

## 3. Limitations

- **The 502 root cause is infrastructure, not code** (see §4 below):
  `render.yaml` provisions no Strapi service and sets no `STRAPI_*` env vars,
  so Django falls back to `http://localhost:1337` and every CMS read refuses.
  The proxy, the public feeds and both frontends handle that honestly.
- No browser/e2e harness in the repo. The verification above used a temporary
  local stack (SQLite settings module + seeded QA data + CDP-driven headless
  Edge) which was deleted afterwards; it is not committed and not part of CI.
  Responsive behaviour was checked at 390px and 1280px width only.
- The portfolio holds text and a link, not uploaded files — this host has no
  persistent disk, so a file would not survive a redeploy.
- Grade "activity type" is stored as a `[Type]` prefix on `remarks` until a
  dedicated model exists; the table reads it back into an Activity chip.
- Guidance Students directory is built from guidance records, not the
  enrollment roster (the page footer says so). A roster view is a product
  decision.
- Faculty assessments were not collapsed (the reviewer flagged guidance's
  page only); the same pattern is available on request.

## 4. What to do about Strapi (the 502)

The content 502 is **not a bug to code around** — `render.yaml`
(`C:\Users\Lay\AEGIS\render.yaml`) defines only the Django web service and
Supabase. There is no Strapi service and no `STRAPI_BASE_URL`,
`STRAPI_API_TOKEN` or `STRAPI_WEBHOOK_SECRET`, so Django defaults to
`http://localhost:1337` and every CMS read refuses within seconds.

To fix it, all inside AEGIS:

1. **Provision Strapi** (the `cms/` folder already contains the project) with
   its own Postgres. On Render: a new `web` service, `rootDir: cms`,
   start `npm run start`, listening on `$PORT`.
2. **Set the Django service env vars** (`STRAPI_BASE_URL`,
   `STRAPI_API_TOKEN`, `STRAPI_WEBHOOK_SECRET`) so the proxy can reach it.
3. **Set the Strapi service env vars** (`AEGIS_WEBHOOK_URL`,
   `AEGIS_WEBHOOK_SECRET`, and the DB block) from `cms/.env.example`, and let
   Strapi bootstrap write its API token into its `.env` (the dev settings
   already read `cms/.env` as a fallback).
4. **Redeploy both**, then confirm `/api/v1/cms/announcements/` returns 200.
   The admin Content screen, the landing page and the notifications the
   webhook emits all start working with no further code change.

Until then the system behaves honestly: "Content service is temporarily
unavailable" instead of a fake empty school.
