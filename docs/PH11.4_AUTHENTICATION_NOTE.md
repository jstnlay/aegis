## 1. Goal

Turn the PH11.3 auth foundation into the real authentication experience:
login, token lifecycle, `/me` bootstrap, restricted (password-change) flow,
logout, session-expiration handling, and protected-route behavior — all on the
PH11.2 approved design system, with focused tests and an Impeccable pass.

## 2. What was implemented

### 2.1 Login screen — `src/routes/pages/LoginPage.tsx`

- Card-presented login form (`w-full max-w-md`) with the AEGIS graduation-cap
  brand mark in warm primary maroon.
- Fields: **email** (`type="email"`, `autoComplete="email"`,
  `inputMode="email"`) and **password** (`type="password"`,
  `autoComplete="current-password"`).
- Validation: react-hook-form + Zod (`@hookform/resolvers/zod`) —
  required email, valid email, required password. `mode: "onBlur"` so inline
  messages appear after the field is left, not while typing.
- Submit: full-width primary button; loading state shows a spinner and
  "Signing in…", disables the inputs, and sets `aria-busy` on the form.
- API integration: `useAuth().login(email, password)`.
- Error state: server message rendered in a `role="alert"` block (destructive
  tones); API errors normalized through `normalizeApiError` (a
  `password_change_required`-style 401 can never display raw backend text).
- Routing: authenticated → `/app`; restricted → `/change-password`;
  unauthenticated sees the form.

### 2.2 Change-password screen — `src/routes/pages/ChangePasswordPage.tsx`

- Same card language: **current password**, **new password**, **confirm new
  password**, with `autoComplete` set to `current-password` / `new-password`.
- Validation: new password required + min length 8 (matches the common DRF/SHS
  floor; the backend remains authoritative), confirmation must equal new
  password (`z.refine`).
- API integration: `useAuth().changePassword(current, new)`.
- Success transition: a confirmation card ("Password updated") with
  **Continue to AEGIS**, then the normal authenticated route. The success card
  renders explicitly so it is not skipped by the authenticated redirect
  (check order: success first, then `isAuthenticated`).
- Escape hatch: "Sign in with a different account" calls `useAuth().logout()`
  so a stuck restricted user can return to login.
- Guarded: restricted users only; authenticated users redirect to `/app`,
  unauthenticated users redirect to `/login`.

### 2.3 Auth state behavior

PH11.3's state machine is reused unchanged:

```
loading → unauthenticated | authenticated | restricted
```

- **Unauthenticated** → login only.
- **Authenticated** → `/app` (AppShell with placeholder Dashboard — as at
  PH11.4; PH11.5 and PH11.6 replaced the placeholder with the role-aware shell
  and real role dashboards).
- **Restricted** (`must_change_password`) → password-change flow; normal
  protected routes redirect to `/change-password`.
- Successful password change clears the restricted gate and becomes
  `authenticated` (context re-fetches `/me`).
- Session expiration (`runSessionExpiredHandlers`) → `unauthenticated` → login.

### 2.4 Token handling / refresh

No change to the PH11.3 token architecture. Refreshes use the stored refresh
token, persist the rotated pair, retry the original request once, are
single-flight (no raced refresh calls), and never refresh when the backend
says "Password change required." Ultimate refresh failure → token clear →
session-expired handlers → login. No infinite retries.

### 2.5 Logout

`AuthContext.logout` now wraps the server call in a best-effort try/catch so
local auth state is always cleared even when the logout request fails (per the
spec: "clear local authentication state even if the logout request itself
fails"). This was the one AuthContext change in this phase.

### 2.6 Error handling

Errors flow through the frozen envelope
`{ success:false, error:{ code, message, details } }` via `lib/error.ts`.
`normalizeApiError` produces typed objects; the auth pages surface only the
safe `message`. No tokens, paths, or stack traces are exposed.

## 3. Backend endpoints integrated

| Endpoint | Method | Used by |
| -------- | ------ | ------- |
| `/api/v1/auth/login/` | POST | `loginRequest` → `useAuth().login` |
| `/api/v1/auth/token/refresh/` | POST | refresh interceptor (`lib/api.ts`) |
| `/api/v1/auth/logout/` | POST | `logoutRequest` → `useAuth().logout` |
| `/api/v1/accounts/me/` | GET | `fetchCurrentUser` → bootstrap + post-login |
| `/api/v1/accounts/password/change/` | POST | `changePasswordRequest` → `useAuth().changePassword` |

No new endpoints were invented.

## 4. Routing

- `/login` — public login form.
- `/change-password` — public route rendered by ProtectedRoute redirects;
  itself redirects to `/app` when authenticated or `/login` when
  unauthenticated.
- `/app` / `/app/dashboard` — protected application area behind
  `ProtectedRoute` + shared AppShell. *At PH11.4 the Dashboard was still a
  placeholder; it was replaced in PH11.5 (role-aware shell) and PH11.6 (real
  role dashboards).*
- Everything else → existing 404.

## 5. Testing

Vitest (jsdom) added as the test runner; `npm test` runs it.

- `src/features/auth/AuthContext.test.tsx` — auth state machine and API flows:
  valid login → authenticated + persisted tokens; invalid credentials stay
  unauthenticated; persisted-session restore (refresh success path);
  stale-session restore falls back to unauthenticated; login + `/me`
  password-change-required → restricted; logout clears state even when the
  server call throws; session-expired event → unauthenticated; successful
  password change clears restricted → authenticated.
- `src/lib/error.test.ts` — `normalizeApiError` / `getFieldErrors` /
  `isHttpError`: 401 invalid-credentials, 401 "Password change required.",
  network failure, field-details validation, idempotence, DRF field
  extraction.
- `scripts/smoke.tsx` — SSR render asserts: `/login` + `/change-password`
  mount, `/app/dashboard` protected skeleton, 404, AppShell landmarks, and
  auth module exports.

Result at PH11.4 completion: **17 tests pass**, smoke passes. This count covered
the auth phase only; later phases added dashboard, navigation, and library tests,
so the present suite is larger. Re-run `npm test` for the current total.

## 8. Deviations & decisions

- **New dependencies (non-speculative, required by scope):** `zod` +
  `@hookform/resolvers` for matching the spec's form-validation requirement;
  Vitest + Testing Library for the required focused tests; `impeccable` as the
  specified review gate. No Tier-2 app libraries (charts, tables, MSW, etc.)
  were added.
- **Password rules:** only a minimal 8-character floor is enforced client-side
  because the spec forbids inventing policies the backend does not support;
  the backend's serializer remains authoritative and its field-error message
  surfaces through the role-alert error.
- **`--force` is intentional on `typecheck`/`build`** (`tsc -b --force`) to
  ensure the whole graph rebuilds from scratch; matches PH11.3's commands.
- **Chunk-size warning** at `vite build` (>500 kB bundle) is pre-existing and
  out of scope — deferred to a later performance pass.
- **Reduced-motion / touch targets:** the app respects the global
  `prefers-reduced-motion` guard from PH11.2; touch targets follow the shared
  design controls (36px) — not widened here to stay consistent with the
  approved system.
- **No new AuthContext state logic** was rearchitected; the earlier web
  bootstrap (`loading → …`) and ProtectedRoute/RequireRole guards are reused
  as-is with zero logic changes except logout robustness.

## 9. Known limitations

- Form field errors are linked to inputs via `aria-describedby` (shadcn/ui
  form convention); they are not announced in a live region. Non-critical and
  tracked for the dedicated accessibility pass.
- Session-expiration protection relies on the interceptor's 401 handling —
  covered at the unit level for the state transition and by
  `ApiClient` behavior; no browser E2E was run (per scope, browser coverage is
  not claimed).
- The Dashboard / role navigations were placeholders by design at PH11.4 and
  were delivered in PH11.5 (navigation) and PH11.6 (dashboards).

## 11. Security note

No backend code was changed. No credentials, `.env` files, or personal paths
were read. Auth secrets live only in browser `localStorage` via the existing
`tokenStorage` (refresh token stored for rotation) and are cleared on logout
or session expiry.
