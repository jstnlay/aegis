# PH11.7 — Academics & Attendance (Domain Batch A)

Verified implementation boundaries for the student and faculty Academics and
Attendance surfaces. Every claim below was read from the backend source before
being built; nothing here is inferred from the prototype.

## 1) Verified backend contracts

### Academics

| Fact | Value |
| --- | --- |
| Routes | `/api/v1/academics/{academic-years,grade-levels,sections,subjects,subject-assignments,schedules,grading-periods,enrollments,grades}/` |
| Grade statuses | `draft`, `submitted`, `finalized` (`Grade.StatusChoices`) |
| Faculty write | `POST /academics/grades/encode/` only — always creates `status=draft` |
| Encode payload | `student`, `subject_assignment`, `grading_period` required; `score`, `letter_grade`, `remarks` optional |
| Encode validation | assignment must belong to caller; student actively enrolled in the assignment's section for the matching academic year; unique on (student, subject_assignment, grading_period) |
| Faculty non-capabilities | no grade edit, no `draft → submitted` transition, no finalize |
| Finalize | `POST /academics/grades/{id}/finalize/` is `IsAdminUser` and requires `submitted` |
| Grade filters | `student`, `subject_assignment`, `grading_period`, `status` — single value only. **`status__in` is not supported** |
| `grades/batch-import/` | declared, returns HTTP 501 |

`Enrollment.student` is the **StudentProfile** UUID, not the User UUID.
De-duplicate on `student` among active (`is_active`) enrollments.

`SectionSerializer` fields: `id`, `name`, `grade_level`, `grade_level_name`,
`academic_year`, `adviser`, `adviser_name`. There is no `enrollment_set`.

`EnrollmentViewSet` implements **no** query-parameter filtering — only role
scoping — so a `?section=` request is silently ignored and returns every visible
enrollment. Section narrowing is therefore done client-side.

### Attendance

| Fact | Value |
| --- | --- |
| Routes | `/api/v1/attendance/records/`, `/api/v1/attendance/summary/` |
| Statuses | `present`, `late`, `absent` |
| Uniqueness | one record per student per date (409 on duplicate) |
| Future dates | rejected by `AttendanceRecordSerializer.validate_date` |
| Faculty create | allowed only in sections they advise or teach |
| Faculty update/delete | only when `recorded_by.user === caller` (403 otherwise) |
| Student read | own records only |
| Record filters | `student`, `section`, `status`, `date_from`, `date_to` |
| Summary | **bare array**, no pagination envelope |

Summary fields: `student`, `student_name`, `student_id_code`, `section_name`,
`present_count`, `late_count`, `absent_count`, `total_records`. It is grouped by
**student + section**, so a multi-section student legitimately produces several
rows. Counts reflect existing records, not school days.

`AttendanceRecordSerializer` marks `recorded_by` read-only — the client must
never send it.

## 2) `score` arrives as a JSON string

`Grade.score` is a `DecimalField`. The project never sets
`COERCE_DECIMAL_TO_STRING`, so DRF's default (`True`) applies and the API emits
`"85.00"` rather than `85`. Verified by running the serializer directly.

This is a live hazard, not a theoretical one: arithmetic on the raw value
string-concatenates and yields `NaN`.

```
0 + "85.00" + "90.00"  ->  "085.0090.00"
"085.0090.00" / 2      ->  NaN
```

PH11.6's `student/api.ts` `averageGrade` fallback does exactly this reduce when
`/analytics/students/{id}/metrics/` reports `has_data: false`. `normalizeScore`
is the single boundary that prevents recurrence: it accepts
`string | number | null | undefined`, returns `number | null`, and treats
unparseable input as *no data* rather than letting `NaN` leak into an average.
`features/academics/api.test.tsx` locks this in.

### Score scale: 0–100, not a percentage ratio

`Grade.score` is `DecimalField(max_digits=5, decimal_places=2)` and
`GradeSerializer` validates `0 <= score <= 100`. It is a raw points value, not a
0–1 ratio, so percentage formatting (`formatPercent`, which appends `%`) would
assert a unit the backend never states. The grade table header reads
"Score (0–100)", cells render `score.toFixed(2)`, and the student average card
is captioned "out of 100". A null score stays "Not recorded".

## 3) Frontend implementation

### `src/features/academics/api.ts`

Types mirror serializer `Meta.fields` exactly. Hooks:

- `useStudentGrades(studentId)` — requests `?status=finalized&student=<uuid>`.
  Server-side `status` is used deliberately: there is no `status__in`, and
  unreleased work must not be fetched only to be discarded.
- `useFacultyGrades()` — fetched unfiltered and partitioned client-side, so one
  request yields both rows and per-status counts.
- `useSubjectAssignments`, `useGradingPeriods`, `useSections`
- `useEnrollmentsInSection(sectionId)` — client-side section narrowing.
- `useEncodeGrade()` — the only grade write.

### `src/features/academics/AcademicsPage.tsx`

- **Student**: finalized grade record plus the mean of recorded scores.
- **Faculty**: encode form + record table with draft/submitted/finalized
  counts, and an explicit note that this API has no faculty edit, submit, or
  finalize transition.
- **Admin**: the existing documented placeholder. PH11.7 implements the student
  and faculty surfaces only; showing admin a student-shaped view would resolve
  no StudentProfile.

### `src/features/attendance/api.ts`

Records with filters, summary as a bare array, and create/update/delete
mutations. Update and delete target `/attendance/records/{id}/` only, mirroring
the backend's self-scoped checks.

`useUpdateAttendance` and `useDeleteAttendance` are kept because the endpoints
are verified, but **PH11.7 has no UI caller for them** — see below.

### `src/features/attendance/AttendancePage.tsx`

- **Student**: own records and the per-section summary table.
- **Faculty**: recording form plus a read-only records table.

#### Why faculty get no edit/delete buttons

`AttendanceRecord.recorded_by` is a `FacultyProfile` primary key, while
`currentUser.id` is a `User` primary key. They are different ID spaces and
cannot be compared. `/accounts/me/` returns a bare `User` payload with no
FacultyProfile identifier, so the frontend has no verified way to learn the
caller's FacultyProfile UUID. Matching on `recorded_by_name` instead would be
name inference, not identity, so it is not used.

The honest result: faculty can **create** and **read** records they are
authorized for, and edit/delete controls are withheld entirely. The backend's
self-scoped `PATCH`/`DELETE` guards (`recorded_by.user === caller`, else 403) are
untouched. The page states this limitation in the records card so the missing
control reads as a deliberate boundary rather than an unfinished screen. A
test pins the trap case where `recorded_by` happens to string-match the caller's
User id: no actions appear.

### Navigation and routes

- Student gains **Academics** and **Attendance** as available links.
- Faculty gains **Attendance** as available.
- Parent, admin, and guidance Attendance entries stay `planned` via a separate
  `ATTENDANCE_PLANNED` item, so no link can bounce off `RequireRole`.
- `/app/academics` → `student`, `faculty`, `admin`; `/app/attendance` →
  `student`, `faculty`.

Faculty attendance tests additionally pin the ownership decision and the
selector:

- no raw UUID input; the student field is a `Select`
- selecting a section loads its enrollments and offers `name — student_id`
- `is_active === false` enrollments are excluded from the selector
- the create payload is exactly `{ student, section, date, status }`
- the date input's `max` equals today
- a backend 409 duplicate surfaces its message
- **no** edit/delete control or Actions column appears even when `recorded_by`
  string-matches `user.id`
- the records card explains why edit/delete are withheld

Radix `Select` renders its content in a portal and scrolls the focused option
into view on open, which jsdom cannot do. `src/test/setup.ts` therefore shims
`scrollIntoView` alongside the existing pointer-capture shims, and the test
helper waits for each trigger to become enabled before firing its open key —
a disabled trigger ignores key events, which otherwise looks like a broken
component.
