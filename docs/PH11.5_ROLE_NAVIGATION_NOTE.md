Status: **complete** · Owner: frontend track · Scope: `frontend/` only — the
backend, API contract, and CMS are untouched.

## 1. Goal

Turn the PH11.3 frontend foundation into a real role-aware application shell with:
- A single shared AppShell serving all five roles (`student`, `parent`, `faculty`, `guidance`, `admin`) — no per-role shells.
- Centralized role-aware navigation model (`src/lib/navigation.ts`) as single source of truth for Sidebar + page-title lookups.
- Five role-specific landing areas (`src/routes/pages/RoleLandingPage.tsx`) using registered role labels and authentic "Coming Soon" lists.
- RequireRole guards around role-specific routes (`/app/academics`).
- Responsive sidebar that moves to a fixed off-canvas position on mobile.
- Impeccable design quality pass.

## 2. What was implemented

### 2.1 Centralized navigation model — `src/lib/navigation.ts`

- Export types: `NavItemStatus`, `NavItem`, `NavGroup`.
- Public API:
  - `getVisibleNavigationForRole(role: Role) — readonly NavGroup[]`
  - `getNavItemsForRole(role: Role) — readonly NavItem[]`
  - `isRouteVisibleToRole(role: Role, route: string) — boolean`
  - `itemHref(item: NavItem) — string` with base path `/app/`
  - `getPageTitle(pathname: string) — string` for header integration.
- Item status semantics:
  - `"available"` — real screen/route exists (`dashboard` for everyone, `academics` for faculty/admin).
  - `"planned"` — documented placeholder; no fake route created, never linked.
- Resolution rules: groups with no visible items are dropped, planned items are shown as roadmap entries.

### 2.2 Serverless role-aware navigation trees

- One tree per role (`STUDENT_NAVIGATION`, `PARENT_NAVIGATION`, `FACULTY_NAVIGATION`, `GUIDANCE_NAVIGATION`, `ADMIN_NAVIGATION`).
- Backend authorization remains authoritative: navigation model controls only frontend UX.

### 2.3 Sidebar — `src/components/layout/Sidebar.tsx`

- Consumes `getVisibleNavigationForRole(user.role)`.
- Available items render as `NavLink` with active state, `aria-current="page"`.
- Planned items render as muted non-navigable helper entries with "Planned" badge.
- Mobile behavior:
  - Under `lg` breakpoint; `max-lg:fixed max-lg:inset-y-0 max-lg:left-0 max-lg:-translate-x-full`.
  - Backdrop overlay appears when `open=true`.
- Prev PH11.5 fix: sidebar now correctly fixed (out of flow) on mobile — CDP measured doc.scrollW=390, overflowX=false.

### 2.4 Header — `src/components/layout/Header.tsx`

- Consumes `getPageTitle()` from navigation config.
- Shows user name and role via `useAuth()`.

### 2.5 AppShell — unchanged (shared, PH11.3)

- Structure: skip link, dark sidebar, top bar, main outlet.
- Placeholder home at `/app/dashboard`.

### 2.6 Role landing pages — `src/routes/pages/RoleLandingPage.tsx`

- One shared landing that takes `role` prop and renders role-specific content.
- Regroups all 5 roles:
  - Student Portal — `ROLES.student`, book icon, "Student Portal" + role badge + "Student Department".
  - Parent Portal — `ROLES.parent`, users icon, "Parent Portal" + role badge + "Parent Department".
  - Faculty Dashboard — `ROLES.faculty`, clipboard-check icon, "Faculty Dashboard" + role badge + "Faculty Department".
  - Guidance Center — `ROLES.guidance`, message-square icon, "Guidance Center" + role badge + "Guidance Department".
  - Administration Panel — `ROLES.admin`, settings icon, "Administration Panel" + role badge + "Administration Department".
- Role-specific greeting from `userDisplayName(user)`.
- Not complete dashboards: honest "Coming Soon" feature lists per role, no fabricated stats/charts.

### 2.7 First-domain documented placeholder — `src/routes/pages/AcademicsLandingPage.tsx`

- PH11.6 first implementation domain.
- Honest "Getting started" context: academic years, grade-levels, sections, subjects, subject assignments, schedules, grading periods, enrollments, grade encoding.
- Consent mode: PH11.3 landing + this page gives navigation/mechanical foundation for later feature work.

### 2.8 Role guard — unchanged from PH11.4

- `RequireRole(allowedRoles[])` wrapped around `/app/academics`.
- **At PH11.5**, an unauthorized role rendered `Navigate to="/app/dashboard"`.
  This target has since changed: a role-guarded route now redirects to `/app`,
  which resolves through the dashboard index to the user's own role dashboard.
- Integrated via `useAuth()` checks.

### 2.9 Routing table — `src/routes/routes.tsx`

**As of PH11.5:**

- `LoginPage` at `/login`, `ChangePasswordPage` at `/change-password`.
- `/` → `ProtectedRoute` → `AppShell`, root → `Navigate to="/app"`.
- `/app/dashboard` → `RoleLandingPage` for all roles.
- `/app/academics` → `RequireRole(["faculty", "admin"])` → `AcademicsLandingPage`.
- Unknown routes continue to use shared `NotFoundPage`.

**Current routing reality (PH11.6+ — supersedes the table above).** The five
role dashboards are nested children of `/app/dashboard`, each individually
guarded, with a redirect component on the index that sends each role to its own
dashboard:

```
/login                                     LoginPage
/change-password                           ChangePasswordPage
/ (ProtectedRoute)
  /app (AppShell)
    index                            -> /app/dashboard
    /app/dashboard (RoleLandingPage + <Outlet/>)
      index                          -> RoleDashboardRedirect (role -> own route)
      /app/dashboard/student         RequireRole[student]  -> StudentDashboard
      /app/dashboard/parent          RequireRole[parent]   -> ParentDashboard
      /app/dashboard/faculty         RequireRole[faculty]  -> FacultyDashboard
      /app/dashboard/guidance        RequireRole[guidance] -> GuidanceDashboard
      /app/dashboard/admin           RequireRole[admin]    -> AdminDashboard
    /app/academics                    RequireRole[faculty, admin] -> AcademicsLandingPage
*                                      NotFoundPage
```

An unauthorized role access now redirects to **`/app`**, which lands on that
role's own dashboard via the index redirect. `RoleLandingPage` remains as the
`/app/dashboard` element and renders the matched child through `<Outlet />`; its
"Coming Soon" content is now only a fallback when no child route matches.

## 6. Impeccable UX refinements (PH11.5)

### 6.1 Tiny text correction

- Sidebar group headings, brand subtitle, and footer used `text-2xs` (10px), flagged as `tiny-text` and `undersized-ui-text`.
- Raised to `text-xs` (12px) to meet legibility expectations for nominal UI labels.

### 6.2 Text overflow fix (mobile)

- Pre-existing bug: Sidebar was `fixed` only when `open=true`, otherwise `static`, squeezing the main column to ~134px on mobile (<1024px).
- CDP measurement showed `doc.scrollW=390, clientW=390 overflowX=true` with `li` overflow 20–23px.
- Fix: applied `max-lg:fixed max-lg:inset-y-0 max-lg:left-0 max-lg:-translate-x-full` to Sidebar and `open && "max-lg:translate-x-0"` to open state.
- CDP post-fix: `doc.scrollW=390, clientW=390 overflowX=false`, all feature list items fully inside card (`right=358, card.right=374`), no text spill.

### 6.3 Preemptive text-overflow guard

- Added `min-w-0` to unordered feature list items (`<ul> li`) to satisfy flex child shrinking and avoid future speculative overflows.

## 7. Deviations & decisions

- **One shell vs one per role**: Decided to keep PH11.3's single shared `AppShell` for consistency and code reuse — role specificity arrives via visibility logic and landing content, not separate components.
- **Role labels**: Used existing `ROLES.*` enum values (`student`, `parent`, `faculty`, `guidance`, `admin`) from PH11.4 — labels handled by `ROLE_LABELS` helper.
- **Planned items never become fake routes**: Intentional. Planned items are shown as roadmap entries and never exposed as navigable links.
- **Responsive sidebar fixed positioning**: Chosen to match PH11.2's "Static sidebar on desktop, fixed off-canvas on mobile" — per CDP measurement and Accordian-style mobile drawers.
- **Tiny text undervalued in original PH11.4**: This PH raised baseline `text-2xs` → `text-xs` only for nominal UI labels (group headings, subtitle, footer). Content remains PH11.2.
- **Impeccable false positives**: Only `nested-cards` remains — confirmed by CDP (`cardCount=1`), false positive from static preview-only measurement.
