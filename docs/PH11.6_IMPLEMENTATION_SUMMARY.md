## 3. DASHBOARDS AND REAL API PATHS

All frontend paths are relative to `VITE_API_BASE_URL` (default
`http://localhost:8000/api/v1`). Every path below was confirmed against the
backend URL configuration/serializers (see §4). The earlier `/enrollments/`,
`/grades/`, `/subject-assignments/`, `/sections/`, `/performance/`, and
`/progress/` paths were wrong and have been removed from this document.

### 3.1 Student — `StudentDashboard.tsx`

| Surface             | Request                                                          |
| ------------------- | ---------------------------------------------------------------- |
| StudentProfile UUID | `GET /academics/enrollments/` (all pages; own enrollments)       |
| Average Grade       | `GET /analytics/students/<studentProfileUUID>/metrics/`          |
| Academic Progress   | `GET /academics/grades/?status=finalized&student=<uuid>` (all pages) |
| Grading periods     | `GET /academics/grading-periods/` (all pages)                    |
| Attendance          | `GET /attendance/summary/?student=<uuid>` (bare JSON array)      |

Semantics:
- The analytics route uses the **StudentProfile UUID**, resolved from the
  student's own enrollment (`enrollment.student`), not the auth User UUID.
  `EnrollmentViewSet.get_queryset` scopes students to their own enrollments.
- "Average Grade" prefers `data.overall_average` from the metrics endpoint and
  falls back to the mean of finalized grade scores for the selected period. It
  is **not** labelled GPA anywhere.
- Subject rows come from actual finalized `Grade` records.
- Grading-period progress is derived only from available finalized grades.
- Attendance is computed client-side as `(present + late) / total_records`.
  The backend explicitly does **not** define an attendance-rate formula
  (`AttendanceRecordViewSet.summary` returns raw counts only); the label here
  is therefore a frontend-derived rate, not a backend-provided `attendance_rate`
  field.

### 3.2 Parent — `ParentDashboard.tsx`

| Surface             | Request                                                        |
| ------------------- | -------------------------------------------------------------- |
| Linked Students     | `GET /academics/enrollments/` (all pages; scoped to linked kids) |
| Child selection     | Re-runs the Student data set for the selected child's UUID     |
| Attendance / Grades | Same student endpoints as §3.1 for the selected child          |

Semantics:
- `EnrollmentViewSet.get_queryset` scopes parents to linked students;
  `useLinkedStudents` deduplicates by the `student` field (StudentProfile UUID),
  never the Enrollment PK.
- Child selection swaps `selectedChildId`, which re-keys every child query.

### 3.3 Faculty — `FacultyDashboard.tsx`

| Surface             | Request                                                     |
| ------------------- | ----------------------------------------------------------- |
| Total Students      | `GET /academics/enrollments/` (all pages)                   |
| Pending Grades      | `GET /academics/grades/?status=draft` (uses `count`)        |
| Pending Submissions | `GET /academics/grades/?status=submitted` (uses `count`)    |
| Subject Assignments | `GET /academics/subject-assignments/` (all pages)           |
| Sections            | `GET /academics/sections/` (all pages)                      |

Semantics:
- Total Students = size of the Set of `enrollment.student` where
  `is_active === true` (unique active StudentProfile UUIDs).
- Pending totals use the DRF `count` field, which is the full filtered total
  even when results are paginated — not `results.length`.

### 3.4 Guidance — `GuidanceDashboard.tsx`

| Surface              | Request                                        |
| -------------------- | ---------------------------------------------- |
| Risk alerts          | `GET /guidance/risk-alerts/` (all pages)       |
| Consultations        | `GET /guidance/consultations/` (all pages)     |
| Assessment completion| `GET /assessments/assessment-results/` (all pages) |

Semantics (matching the task rules):
- Active Cases = risk alerts with status in `active`, `under_monitoring`,
  `escalated`.
- At-Risk Students = **distinct** `student` UUIDs with `risk_level` in
  `moderate`, `high`.
- Pending Follow-up = consultations with status in `ongoing`, `follow_up`.
- Assessment Completion = `completed / total` `AssessmentResult` records, shown
  as a percentage. The UI label reads "Completed vs started assessments".
- No `risk_score`, AI recommendation, AI-generated result, or risk provenance is
  fabricated; cards render only backend fields (`risk_level`, `risk_factors`,
  `status`, `student_name`, timestamps).

### 3.5 Admin — `AdminDashboard.tsx`

| Surface               | Request                                          |
| --------------------- | ------------------------------------------------ |
| Overall Grade Average | `GET /analytics/school-wide/` → `overall_grade_average` |
| Total Students        | `GET /analytics/school-wide/` → `total_students` |
| Grade Levels          | `GET /analytics/school-wide/` → `grade_levels`   |
| Risk Distribution     | `GET /analytics/risk-distribution/` → `distribution` |
| Low-Performance       | `GET /analytics/low-performance/`                |

Semantics:
- Admin uses the exact `overall_grade_average` field.
- Risk distribution uses the backend's actual structure
  `{ low, moderate, high, insufficient_data }`.
- Low-performance entries use the backend fields
  `{ student_id, student_name, average }` only. **No** risk level is invented
  for low-performance students.
- The backend low-performance endpoint takes an optional `?threshold=` query
  parameter (default 75); there is no `/<threshold>` path segment. The frontend
  calls `/analytics/low-performance/` and relies on the backend default.

## 4. RESPONSE ENVELOPE AND PAGINATION HANDLING

- Analytics endpoints return `{ "status": "ok", "data": ... }`; the admin and
  student metrics clients unwrap `.data` before use.
- DRF `DefaultRouter` list endpoints return
  `{ count, next, previous, results }`. Aggregations that need every record go
  through `fetchAllPages`.
- `GET /attendance/summary/` is a **bare JSON array**, not paginated, and is
  consumed directly.

`frontend/src/lib/pagination.ts` exports a single reusable helper:

```
fetchAllPages<T>(url, { signal })
  -> { results: T[], count: number }
```

It requests the initial page, appends results, follows the returned absolute
`next` URL verbatim, stops when `next === null`, preserves the authoritative
`count`, preserves typing, and has a runaway guard. Unit-tested in
`frontend/src/lib/pagination.test.ts` (multi-page follow, `next === null`
termination, authoritative `count`).

Endpoints using `fetchAllPages` for full aggregation:
`/academics/enrollments/`, `/academics/grades/` (student finalized),
`/academics/grading-periods/`, `/academics/subject-assignments/`,
`/academics/sections/`, `/guidance/risk-alerts/`, `/guidance/consultations/`,
`/assessments/assessment-results/`.

Endpoints intentionally read once because a paginated `count` is authoritative
and no per-row aggregation is needed: `/academics/grades/?status=draft` and
`?status=submitted`.

Pagination was additionally verified **live** against the running backend by
walking every page until `next === null` and comparing the collected result
count to the authoritative `count`:

| Endpoint                   | Pages | Collected | Authoritative `count` |
| -------------------------- | ----- | --------- | --------------------- |
| `/audit-logs/?page_size=5` | 3     | 11        | 11                    |
| `/grade-levels/`           | 3     | 3         | 3                     |
| `/academic-years/`         | 2     | 3         | 3                     |

The dev dataset is too sparse for any *dashboard* endpoint to span multiple
pages, so live multi-page behaviour is proven on these larger collections plus
the unit tests on the helper itself.

## 7. DEFECTS FOUND AND FIXED DURING BROWSER VERIFICATION

### 7.1 False "Unable to load" on Student and Parent — FIXED

**Severity: high (user-visible false error on two dashboards).**

The attendance query in `src/features/student/api.ts` returned `undefined` when
the backend responded `200 []` (a student with no attendance records):

```
Query data cannot be undefined. Please make sure to return a value other
than undefined from your query function.
```

TanStack Query v5 treats a resolved `undefined` as an **error**. Because
`useStudentDashboardData` folds `attendanceQuery.error` into a single shared
`error` flag, this poisoned unrelated sibling sections even though every request
had succeeded — the browser showed:

- Student: `Academic Progress` → "Unable to load academic progress. Please try again."
- Parent: `Academic Progress` and `Recent Grades` → the same false error,
  while the metrics and grade requests were all `200`.

**Fix:** return `null` (the codebase's established "no data" value) and type the
query `AttendanceSummary | null`. The comment at the call site records why
`undefined` must never be reintroduced.

Regression tests in `src/features/student/api.test.tsx` assert the query
resolves to `null` and stays out of an error state, and that a genuine `0%`
rate (all records absent) is still preserved as `0` rather than collapsing to
`null`. The regression test was confirmed to **fail** when the fix is reverted
and to pass with it applied.

### 7.2 Parent dashboard had no "Academic Progress" section — FIXED

**Severity: medium (feature gap against the task spec).**

Task Step 3 lists Academic Progress for the parent role, but `ParentDashboard`
rendered only Average Grade, Attendance Rate, and Recent Grades; the per-period
`periods` data from `useStudentDashboardData` was fetched but never rendered.
The section now renders. Verified in the browser: the parent dashboard shows
`Academic Progress → No grading period data available` on empty data.

### 7.3 Letter-grade badge used runtime-composed Tailwind classes — FIXED

**Severity: medium (silent visual failure).**

`ParentDashboard` previously built `` `bg-${letter}-100 text-${letter}-800` ``
at runtime. Tailwind only emits utilities it can find as complete literals, so
those classes were **never generated**; the badge rendered with the neutral
fallback for every grade. Verified against the compiled bundle both before and
after the fix — the legacy dynamic classes are absent and all 15 static
badge classes are present.

**Fix:** `src/lib/grade-badge.ts` provides a static, typed map
(`letterGradeBadgeClass`) covering the standard Philippine grading scale
(A/B/C/D/F with `+/-`), plus `INC`/`NG` and neutral fallbacks for missing or
unrecognised values (`letter_grade` is a free-form `CharField`, not an enum).
`src/lib/grade-badge.test.ts` locks the map down and asserts no returned class
ever contains an unresolved template placeholder.

### 7.4 "0" shown where the metric was genuinely absent — FIXED

`AdminDashboard` (`overall_grade_average || 0`) and `ParentDashboard`
displayed `0.00%` / `0.0%` when the backend had no data, claiming a measured
zero. Absent values now render as `N/A`, while a **genuine** zero is still
rendered as `0`. Verified in the browser: admin's Overall Grade Average is `N/A`
(not `0`), and the three risk counts correctly show real `0`s.

### 7.5 Student "Total Subjects" subtitle was inaccurate — FIXED

The card read "Completed assessments" while the value is the count of distinct
subjects **with finalized grades**. The subtitle now reads
"Subjects with finalized grades".

### 7.6 `w-max` email badge overflow at 390px — NOT A DEFECT (verified safe)

Each dashboard header renders a `truncate` badge containing the user's email,
which was flagged as a possible 390px overflow. Verified in the browser at
390px: `documentElement.scrollWidth === 390` for all five roles, `main` width is
exactly 390, and zero content elements extend past the viewport. The badge
truncates rather than overflowing.

## 8. KNOWN NON-BLOCKING WARNINGS

1. **Vite HMR WebSocket errors in the dev console.** The dev server's HMR
   socket fails in this sandbox (`WebSocket connection to 'ws://127.0.0.1:5173'
   failed` / `[vite] failed to connect to websocket`). This is a dev-tooling
   transport limitation, not an application fault: all XHR/fetch requests return
   `200`, and the app renders and interacts fully. No application-level console
   error was observed in any of the five role sessions.

2. **Guidance assessment-completion scope.** `AssessmentResultViewSet` scopes
   guidance/faculty to `assessment__created_by = user`, so the completion rate
   reflects the current counselor's visible results, not all school results.
   This is a backend access-control consequence, not a frontend defect.

3. **Build chunk-size advisory.** The production JS bundle is ~594 kB
   (>500 kB) — a Vite advisory, not a failure. Severity: non-blocking.

### Impeccable review

`impeccable context` reported no PRODUCT.md / DESIGN.md (scoped command, so
proceeded using code as context, as the context output directs). The mechanical

directories returned `[]` with exit code 0. A login-URL detector run reported a
`nested-cards` warning, which DOM inspection disproved: the login page contains

The detector does not catch runtime-composed Tailwind classes; that class of
defect (§7.3) was verified manually against the compiled CSS bundle.

### 11.2 Accessibility evidence — and its limits

**13 affected CSS/class combinations were verified against the built CSS using
colorjs.io.** The method was static: token values were parsed from the compiled
`dist/assets/index-*.css`, class lists were resolved through the project's own
`tailwind-merge` (so the losing declaration in each conflicting pair was
identified, not guessed), and colours were converted and composited by
colorjs.io.

**Browser verification was attempted but could not be completed.** A temporary
contrast harness was blocked by the browser tool's URL policy — both the
`file://` form and a `http://127.0.0.1` form were refused. The harness was never
rendered or viewed. **No result below is browser-confirmed**, and none of these
figures come from a rendered browser.

All affected text was assessed against the **4.5:1 normal-text threshold**
regardless of size or weight. PH11.2 §16.2 treats ≥18px (or ≥14px bold) as
"large" and applies 3:1; that relaxation is deliberately **not** relied on here,
so the conclusion does not depend on that wording.

### 11.3 Deliberate deviation from PH11.2 §6.2 — solid badges

PH11.2 §6.2 documents risk levels as **solid** badges: Low → `--success` solid,
Moderate → `--warning` solid, High → `--destructive` solid with stronger weight.

**The implementation does not match that visual requirement.** The risk badges
use a text/outline treatment (`bg-card` + semantic text and border) instead of a
semantic fill. This is a deliberate accessibility trade-off after the tested
solid/tint combinations failed the required contrast under the existing token
values:

- `--warning` (`oklch(0.82 0.15 80)`) is a light amber built for a surface. As
  bare text on a card it measures **1.77:1**, so a solid `--warning` badge can
  only be readable with its paired `--warning-foreground` (16.16:1).
- `--success` (`oklch(0.55 0.16 145)`) is a mid-tone. A solid `--success` fill
  with `--success-foreground` reaches only **4.35:1**, and a `bg-success/10`
  tint only **3.99:1** — both under 4.5:1, and the risk badge renders at
  `text-xs`. `text-success` on the card surface (4.54:1) is the only compliant
  option.
- The three tokens are therefore **not interchangeable in role**, so a single
  uniform solid treatment does not exist for the small risk labels.

Global token values were **not** changed. Restoring solid badges would require a
PH11.2 amendment to the token definitions, not a frontend class change.

Student grade scores were reduced to plain semantic text (no pill, no padding)
as a separate correction; the pre-cleanup filled chips measured 4.35:1 for the
success tier.

### 11.6 Process-safety deviation and unresolved environment observation


The task instructions for that pass explicitly prohibited broad process
termination. The command was issued regardless, and that is a **process-safety

What is **not** claimed: no analysis was performed of which processes were

### 12.1 W1 - Fallback and completed-consultation badge contrast

**STATUS:** IMPORTANT / OPEN

**EVIDENCE:** `frontend/src/lib/status-badge.ts` renders two states as
`text-muted-foreground` on `bg-muted`: the `FALLBACK_CLASS` used when
`riskLevelBadgeClass` receives an unrecognised `risk_level`, and the
`completed` entry of `CONSULTATION_STATUS_CLASSES`. The tokens
(`--muted: oklch(0.967 0.003 265)`, `--muted-foreground: oklch(0.552 0.014 285.9)`)
were independently recomputed from the compiled stylesheet, giving **4.39:1**.
Badge typography is `text-xs` (`frontend/src/components/ui/badge.tsx`), so the
4.5:1 normal-text threshold applies, not the 3:1 large-text relaxation. Both
`.bg-muted` and `.text-muted-foreground` are present in the built CSS, so the
combination renders as written.

This pair is **not** among the 13 PH11.15 risk/score combinations validated in
§11.2, and it was **not** introduced by the PH11.15 changes — it predates them and
originates with the PH11.6 consultation and fallback styling. Nothing here
establishes it as a PH11.15 regression.

**IMPACT:** These two states fall short of the same normal-text contrast target
that the audited PH11.15 combinations were held to. The finding is not remediated
in this documentation-only pass, and no replacement colour is proposed here; a
fix requires a separate implementation decision.

### 12.2 W2 - "Only compliant option" comment wording

**STATUS:** WARNING / DOCUMENTATION

**EVIDENCE:** The comment block in `frontend/src/lib/status-badge.ts` states that
`text-success` on the card surface "is the only compliant option". The supporting
measurements enumerate specific tested candidates: a solid `--success` fill with
`--success-foreground` at 4.35:1, a `bg-success/10` tint at 3.99:1, and
`text-success` on the card at 4.54:1. The first two reproduce; the evidence
therefore establishes that those enumerated candidates fail, which is narrower
than a universal claim that no other compliant implementation exists.

**IMPACT:** The comment's absolute phrasing overstates what was measured and is
inconsistent with the deliberately evidence-bounded wording used in §11.2 and
§11.3. This is a wording issue in a code comment only. `status-badge.ts` was not
modified in this pass.

### 12.3 W3 - `fetchAllPages` iteration cap

**STATUS:** IMPORTANT / OPEN

**EVIDENCE:** `frontend/src/lib/pagination.ts` loops `while (next && guard < 100)`.
The backend paginator (`StandardResultsPagination` in the Django project) sets
`page_size = 20` with `max_page_size = 100`, and `fetchAllPages` does not request a
larger page size, so the helper can stop after roughly **2,000 records** per
endpoint. The helper returns only `{ results, count }` and provides no explicit
truncation or error signal when the guard trips.

**IMPACT:** This is a scalability and data-completeness risk: a large
faculty or guidance aggregate query could return a silently incomplete list while
appearing successful. **No current production failure is claimed and no dataset
size is asserted** — the local dataset is sparse (§10) and the cap was not
exercised. The helper was not modified in this pass; this remains open work for a
later implementation pass.
