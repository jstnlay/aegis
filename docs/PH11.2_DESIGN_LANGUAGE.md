## 1. Design Goals

| Goal | Description |
|------|-------------|
| **Clarity** | Information is immediately scannable. No decoration competes with content. |
| **Consistency** | One shared design system across all five roles. No role-specific visual silos. |
| **Denseness where appropriate** | Tables and data-heavy views are compact. Dashboards are readable but not wasteful of space. |
| **Accessibility** | WCAG 2.1 AA as the target baseline. Every user, regardless of ability, can navigate and understand the interface. |
| **Responsiveness** | Functional from 320px mobile to 1920px desktop (NFR-015). No breakpoint is broken. |
| **Token-driven** | All visual properties derive from a defined token system. No arbitrary values in component styles. |
| **Maintainability** | A student capstone project. The system must be simple enough for one developer to maintain and extend. |
| **Warm professional tone** | Academic/school context. The UI should feel institutional, trustworthy, warm, approachable, and friendly for younger students — while remaining professional for faculty, guidance, parents, and administrators. |

## 2. Design Principles

1. **Content first.** The interface exists to serve data — grades, attendance, risk levels, interventions. Visual elements that do not support comprehension are removed.

2. **Shared system, role-specific content.** All five roles use the same AppShell layout pattern, the same planned component library, the same tokens. Only navigation structure, content scope, and action permissions differ.

3. **Earned complexity.** Simple by default. Complexity (filters, drill-downs, advanced actions) appears only when the user's role and task require it.

4. **Color is never the only signal.** Risk levels, attendance states, grades, and status indicators always have a text label or icon alongside color. This is an accessibility requirement, not a preference.

5. **Consistent spacing over visual drama.** A small, coherent spacing scale replaces arbitrary margins and padding. Every gap between elements is intentional.

6. **Tables stay tables.** Tabular data (grades, attendance records, student lists) remains in table format with horizontal scrolling on small screens. Cards do not replace tables for comparative data.

7. **Motion serves comprehension.** Transitions exist to orient the user (where did this come from, where did it go), not to entertain.

## 3. Visual Direction

### 3.1 Overall Character

The AEGIS interface should feel like a **well-organized institutional system** — closer to a school LMS or student information system than a SaaS marketing product — with a warm, approachable treatment suited to a high school audience.

**Adopt:**
- Clean, warm off-white/white backgrounds for content areas
- Dark sidebar navigation (anchoring, high contrast)
- Warm neutral palette with a restrained maroon brand accent
- Dense but readable tables
- Clear typographic hierarchy
- Minimal decoration
- A brand maroon that is warm and school-appropriate — not overly dark, aggressive, or visually heavy

**Avoid:**
- Heavy gradients on surfaces or headers
- Glassmorphism or frosted glass effects
- Excessive border-radius on cards and containers
- Decorative illustrations in the main UI (SVG icons for function, not decoration)
- Bright or saturated backgrounds behind content
- Shadow-heavy elevation (floating cards over colored backgrounds)
- Dashboard clutter — KPI cards are justified, not decorative
- Treating brand maroon as though it were an error/alert color

### 3.2 Prototype Baseline

The approved prototype (`Final_Revision.pdf`) establishes:

- **Dark sidebar** with role-appropriate navigation items
- **White/light content area** with structured card layouts
- **KPI cards** at the top of dashboards for at-a-glance metrics
- **Tables** for student lists, grades, attendance records
- **Role-specific sections** (e.g., Guidance has risk alerts, Faculty has class summaries)

**Design decisions extending the prototype:**

These entries distinguish what the prototype explicitly defines from what PH11.2 adds to establish a complete design system. The additions below are planned; none are implemented.

| Prototype Element | Planned Implementation | Reason |
|-------------------|---------------|--------|
| Implicit spacing values | Explicit spacing scale (4px base) | Token-driven consistency |
| No visible focus states | Clear keyboard focus indicators | Accessibility (WCAG 2.1 AA) |
| No responsive behavior shown | Full 320px–1920px responsive system | NFR-015 |
| No dark mode shown | Light-only for v1 | See §19.3 — Dark Mode Decision |
| Color semantics not defined | Explicit semantic token system | Prevents inconsistent color usage |

## 4. Typography System

### 4.1 Font Family

```css
--font-sans: "Inter", ui-sans-serif, system-ui, -apple-system, sans-serif;
--font-mono: "JetBrains Mono", ui-monospace, monospace;
```

**Why Inter:**
- Designed specifically for screens at small sizes (9px–24px)
- Excellent legibility in dense tables and data-heavy views
- Large character set supports Filipino/Tagalog diacritics (important for a Philippine school context)
- Free, open source (SIL Open Font License)
- Wide adoption means predictable rendering across browsers
- Tabular figures available via `font-variant-numeric: tabular-nums` for aligned numbers in tables and KPIs
- Not trendy — designed for utility, not fashion

**Why not alternatives considered:**

| Font | Reason Rejected |
|------|----------------|
| System font stack only (no Inter) | Less consistent rendering across OS; smaller x-height at small sizes |
| IBM Plex Sans | Good alternative, but Inter has better small-size rendering and wider community support |
| Source Sans Pro | Older design; Inter is its spiritual successor with improvements |
| Roboto | Associated with Android/Google; less neutral for an academic institution |
| Noto Sans | Good fallback, but Inter has tighter metrics for dashboard use |

### 4.2 Type Scale

| Token | Size | Line Height | Use |
|-------|------|-------------|-----|
| `text-2xs` | 0.625rem (10px) | 1rem | Timestamps, fine print only |
| `text-xs` | 0.75rem (12px) | 1rem | Table cells, captions, metadata |
| `text-sm` | 0.8125rem (13px) | 1.25rem | Secondary text, labels, form hints |
| `text-base` | 0.875rem (14px) | 1.5rem | Body text, table body, form inputs |
| `text-md` | 1rem (16px) | 1.5rem | Page titles, section headings |
| `text-lg` | 1.125rem (18px) | 1.75rem | Dashboard KPI values, card titles |
| `text-xl` | 1.25rem (20px) | 1.75rem | Page-level headings |
| `text-2xl` | 1.5rem (24px) | 2rem | Dashboard page title |

**Why 14px base:** The default body size is 14px to support the data-dense interface. Smaller text is limited to secondary metadata and should remain readable and accessible. The 16px system default is available for user-adjustable settings.

### 4.3 Font Weights

| Token | Weight | Use |
|-------|--------|-----|
| `font-normal` | 400 | Body text, table content |
| `font-medium` | 500 | Labels, navigation items, emphasis |
| `font-semibold` | 600 | Section headings, card titles, button text |
| `font-bold` | 700 | KPI values, page titles |

**Do not use `font-light` (300) or `font-black` (900).** They reduce readability at small sizes and on low-resolution displays.

### 4.4 Typography Rules

- **Text below 10px is not used.** The smallest size (`text-2xs`, 10px) is limited to timestamps and fine print. Smaller text is limited to secondary metadata and should remain readable and accessible; it is never used for primary content.
- **All numeric data uses tabular figures:** `font-variant-numeric: tabular-nums` on tables, KPIs, and any number display.
- **Headings are not bold by default in body text.** Use `font-semibold` for inline emphasis, `font-bold` only for KPI values and page titles.
- **Line length for body text:** max 72 characters (about 600px at 14px). Not critical for dashboard UI but relevant for long-form content (announcements, consultation notes).
- **Filipino/Tagalog support:** Inter covers all diacritical marks used in Filipino. No additional font loading needed.

## 5. Color System

### 5.1 Palette Approach

AEGIS uses a **warm neutral-dominant palette** with a single restrained warm maroon brand accent, supported by a soft rose accent family. This is an institutional application, not a consumer product. The palette prioritizes:

1. Readability (high contrast text on backgrounds)
2. Warmth (school-appropriate, approachable, friendly for younger students)
3. Neutrality (does not distract from data)
4. Status clarity (semantic colors are distinct and meaningful)
5. Accessibility (essential text, controls, and interface elements will use color combinations that meet the applicable contrast requirements; decorative or disabled elements may use lower-contrast values where permitted)

**Brand maroon is NOT the same thing as destructive/error red.**

- **Maroon** is reserved for branding, primary actions, active navigation, selected states, and major interface accents.
- **Stronger red** is reserved for errors, destructive actions, and critical states.

## 8. Spacing and Density

### 8.1 Spacing Scale

The spacing system is primarily based on a 4px scale, with limited smaller values for tight spacing.

| Token | Value | Use |
|-------|-------|-----|
| `space-0` | 0 | — |
| `space-0.5` | 2px | Tight inline spacing (icon to text) |
| `space-1` | 4px | Minimum gap, inline elements |
| `space-1.5` | 6px | Tight component padding |
| `space-2` | 8px | Compact padding, small gaps |
| `space-3` | 12px | Default component padding |
| `space-4` | 16px | Standard gap between related elements |
| `space-5` | 20px | Section internal spacing |
| `space-6` | 24px | Section separation |
| `space-8` | 32px | Major section separation |
| `space-10` | 40px | Page-level spacing |
| `space-12` | 48px | Large page sections |
| `space-16` | 64px | Maximum spacing |

### 8.2 Density Presets

Different contexts require different density levels.

#### Dashboard Density
- KPI cards: `space-6` (24px) gap between cards
- Card internal padding: `space-5` (20px) to `space-6` (24px)
- Section titles: `space-6` (24px) below heading
- Chart containers: `space-4` (16px) internal padding

#### Table Density
- Row height: 40px default (compact: 36px, comfortable: 48px)
- Cell padding: `space-3` (12px) horizontal, `space-2` (8px) vertical
- Header row: `space-3` (12px) vertical
- Table gap (if stacked cards on mobile): `space-3` (12px)

#### Form Density
- Field gap: `space-4` (16px) between form fields
- Label to input gap: `space-1.5` (6px)
- Section heading to first field: `space-6` (24px)
- Button row gap: `space-3` (12px)
- Inline form (filter bar): `space-3` (12px) between elements

#### Sidebar/Navigation Density
- Nav item height: 36px
- Nav item padding: `space-2` (8px) horizontal, `space-1.5` (6px) vertical
- Nav group gap: `space-6` (24px)
- Sidebar width: 240px expanded, 64px collapsed

#### Mobile Density
- Content padding: `space-4` (16px)
- Card gap: `space-4` (16px)
- Bottom nav item: 56px height (touch target)
- Reduced sidebar (drawer on mobile)

## 9. Shape / Radius / Borders

### 9.1 Border Radius Scale

| Token | Value | Use |
|-------|-------|-----|
| `radius-none` | 0 | Tables, code blocks |
| `radius-sm` | 0.375rem (6px) | Buttons, inputs, badges |
| `radius-md` | 0.5rem (8px) | Cards, dialogs, dropdowns |
| `radius-lg` | 0.75rem (12px) | Larger cards, modals |
| `radius-xl` | 1rem (16px) | Avatars (circular) |
| `radius-full` | 9999px | Pills, circular elements |

**Base radius variable:** `--radius: 0.625rem` (10px) — this is the shadcn/ui convention. The scale derives from this.

### 9.2 Border Rules

- **Cards:** 1px solid `--border` (`slate-200`)
- **Inputs:** 1px solid `--input` (`slate-200`), 1px `--ring` on focus
- **Tables:** 1px solid `--border` on header bottom; 1px solid `--border` between rows (subtle)
- **Dividers:** 1px solid `--border` (horizontal rules between sections)
- **No double borders.** One border per element.
- **No border-only cards.** Cards use subtle background difference + border, not border alone.

## 10. Shadows / Elevation

### 10.1 Shadow Scale

AEGIS uses minimal shadows. Most elevation is communicated through background color difference, not shadow.

| Token | Value | Use |
|-------|-------|-----|
| `shadow-xs` | `0 1px 2px oklch(0 0 0 / 0.05)` | Subtle lift on inputs |
| `shadow-sm` | `0 1px 3px oklch(0 0 0 / 0.1), 0 1px 2px oklch(0 0 0 / 0.06)` | Cards at rest |
| `shadow-md` | `0 4px 6px oklch(0 0 0 / 0.07), 0 2px 4px oklch(0 0 0 / 0.06)` | Dropdowns, popovers |
| `shadow-lg` | `0 10px 15px oklch(0 0 0 / 0.1), 0 4px 6px oklch(0 0 0 / 0.05)` | Dialogs, modals |
| `shadow-xl` | `0 20px 25px oklch(0 0 0 / 0.1), 0 8px 10px oklch(0 0 0 / 0.04)` | Full-screen overlays |

### 10.2 Elevation Rules

- **Sidebar:** No shadow. Separated from content by background color difference (dark sidebar, light content).
- **Cards at rest:** `shadow-sm` or no shadow with subtle border. Do not use heavy shadows on every card.
- **Cards on hover (interactive):** Transition to `shadow-md` on hover for clickable cards.
- **Dropdowns/popovers:** `shadow-md` + border.
- **Dialogs/modals:** `shadow-lg` + backdrop overlay.
- **No shadow stacking.** Avoid overlapping shadows from nested elements.

## 11. Motion

### 11.1 Transition Durations

| Token | Duration | Use |
|-------|----------|-----|
| `duration-fast` | 100ms | Button hover, input focus, checkbox toggle |
| `duration-normal` | 200ms | Dropdown open/close, sidebar expand, tooltip show |
| `duration-slow` | 300ms | Dialog enter/exit, page transition, drawer slide |
| `duration-slower` | 500ms | Complex multi-element transitions (if used) |

### 11.2 Easing

| Token | Value | Use |
|-------|-------|-----|
| `ease-default` | `cubic-bezier(0.4, 0, 0.2, 1)` | General transitions |
| `ease-in` | `cubic-bezier(0.4, 0, 1, 1)` | Exiting elements |
| `ease-out` | `cubic-bezier(0, 0, 0.2, 1)` | Entering elements |

### 11.3 Transition Rules

- **Buttons:** `background-color`, `color`, `border-color` — `duration-fast`
- **Inputs:** `border-color`, `box-shadow` — `duration-fast`
- **Cards (hoverable):** `box-shadow`, `border-color` — `duration-normal`
- **Sidebar:** `width` — `duration-normal` (for collapse toggle)
- **Dialogs:** `opacity`, `transform` — `duration-slow`
- **Page content:** No page transition animation. Content swaps instantly.
- **Loading states:** Skeleton screens (static, no pulse animation). Pulse only on skeleton placeholders if used.

### 11.4 Reduced Motion

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}
```

All animations and transitions respect `prefers-reduced-motion`. When the user has requested reduced motion, all transitions are effectively instant.

### 11.5 What Does NOT Animate

- Page navigation (instant swap)
- Table row rendering (instant)
- Data loading (skeleton → content, instant swap)
- Status changes (instant update)
- Toast/notification appearance (appear instantly, may fade out after delay)

## 12. Responsive / Breakpoint Strategy

### 12.1 Breakpoints

| Name | Min Width | Target |
|------|-----------|--------|
| `xs` (default) | 0px | Small mobile |
| `sm` | 640px | Large mobile / small tablet |
| `md` | 768px | Tablet |
| `lg` | 1024px | Small desktop / landscape tablet |
| `xl` | 1280px | Desktop |
| `2xl` | 1536px | Large desktop |
| `3xl` | 1920px | Full HD |

**Note:** Tailwind CSS 4 uses rem-based breakpoints by default. These px values are for reference; implementation uses `sm:`, `md:`, `lg:`, `xl:`, `2xl:` prefixes.

### 12.2 Layout Behavior Per Breakpoint

#### Mobile (< 768px)

- **Sidebar:** Hidden. Replaced by bottom navigation bar (5 items max) or hamburger drawer.
- **Content:** Full width with `space-4` (16px) padding.
- **Tables:** Horizontal scroll with `-webkit-overflow-scrolling: touch`. Table remains a table.
- **Cards:** Full width, stacked vertically.
- **KPI cards:** 2-column grid on small mobile, 1-column on very small (< 380px).
- **Dialogs:** Full-screen or near-full-screen bottom sheet.
- **Forms:** Full width, single column.

#### Tablet (768px – 1023px)

- **Sidebar:** Collapsed (icon-only, 64px width) or hidden with drawer toggle.
- **Content:** Full width minus sidebar.
- **Tables:** Horizontal scroll if columns exceed viewport.
- **Cards:** 2-column grid.
- **KPI cards:** 2–3 column grid.
- **Dialogs:** Centered modal, max-width 480px.

#### Desktop (1024px – 1279px)

- **Sidebar:** Expanded (240px width), persistent.
- **Content:** Remaining width.
- **Tables:** Full width, no scroll needed for typical table configurations.
- **Cards:** 2–3 column grid.
- **KPI cards:** 3–4 column grid.

#### Large Desktop (1280px+)

- **Sidebar:** Expanded (240px).
- **Content:** Max-width container (1200px) centered or full-width with padding.
- **Tables:** Full width.
- **Cards:** 3–4 column grid.
- **KPI cards:** 4 column grid.

### 12.3 Component Responsive Behavior

| Component | Mobile | Tablet | Desktop |
|-----------|--------|--------|---------|
| **Sidebar** | Bottom nav or drawer | Collapsed icon rail | Expanded 240px |
| **Data table** | Horizontal scroll | Horizontal scroll if needed | Full width |
| **KPI cards** | 1–2 columns | 2–3 columns | 3–4 columns |
| **Card grid** | 1 column | 2 columns | 2–3 columns |
| **Form layout** | Single column | Single column, wider | Single or two column |
| **Dialog/Modal** | Full-width bottom sheet | Centered 480px | Centered 560px |
| **Page header** | Stacked (title + actions) | Side-by-side | Side-by-side |
| **Search/filter bar** | Stacked inputs | Inline | Inline |
| **Notifications list** | Full width | Full width | Side panel or full width |
| **Chart containers** | Full width, min-height 200px | Full width | Flexible width |
| **Navigation** | Bottom bar (5 items) | Sidebar (collapsed) | Sidebar (expanded) |

### 12.4 Table Responsiveness

**Tables do NOT become cards on mobile.** The established rule:

- Tables remain tables for all data where tabular comparison is important.
- On screens < 768px, tables get horizontal scroll.
- Critical tables (e.g., attendance recording) may have a simplified "card view" toggle, but the default is always a scrollable table.
- The toggle between table and card view is a user-initiated action, not automatic.

| Size | Height | Padding | Use |
|------|--------|---------|-----|

| `md` | 36px | `space-3` horizontal | Default |

**Button rules:**
- All buttons have visible focus ring for keyboard navigation.

**Input rules:**
- All inputs have visible labels (never placeholder-only).

### 13.3 Select / Dropdown

- Styled consistently with inputs (same height, border, radius).

| Property | Value |

**Card rules:**

## 14. Forms / Tables / Cards / Navigation

### 14.1 Forms

**Form layout:**
- Single column by default.
- Two columns on wide screens (> 1024px) for forms with many fields (e.g., user creation, assessment creation).
- Field groups: related fields grouped with section headings.
- Submit button: sticky at bottom on mobile, right-aligned on desktop.

**Form validation:**
- Inline validation on blur (not on every keystroke).
- Error messages appear below the field.
- Error icon + red border on invalid fields.
- Form-level error summary at top if multiple errors exist.

**Form patterns:**

| Form Type | Layout | Notes |

### 14.2 Tables

**Table structure:**
- Header row: `slate-100` background, `font-semibold`, `text-sm`.
- Body rows: white background, alternating `slate-50` on even rows (optional — can be removed if zebra striping is visually noisy).
- Row hover: `slate-50` background.
- Row height: 40px (compact: 36px).
- Cell padding: `space-3` (12px) horizontal.
- Borders: bottom border only (`slate-200`), no vertical borders.

**Table features:**
- Sortable columns: sort icon (up/down arrows) in header.
- Selectable rows: checkbox column (for bulk actions).
- Expandable rows: + icon to expand row detail (for grades, notes).

- Pagination: always present for list views.
- Empty state: centered message with icon when no data.

**Table density options (user preference or context-driven):**
- Compact: 36px rows, `space-2` vertical padding — for dense data views.
- Default: 40px rows, `space-2` vertical padding — standard.
- Comfortable: 48px rows, `space-3` vertical padding — for readability-focused views.

## 15. Charts and Data Visualization

### 15.1 Chart Library

**Recharts** (as per PH11.1 technology decisions — a confirmed carry-over, not re-decided here). Built on React + D3.

### 15.2 Chart Color Palette

A shared sequential palette (used by every role) for up to 5 data series, designed to remain distinguishable for users with common forms of color-vision deficiency.

| Token | OKLCH | Hex (approx) | Use |
|-------|-------|---------------|-----|
| `chart-1` | `oklch(0.646 0.222 41.1)` | `#e76f51` | Primary data series |
| `chart-2` | `oklch(0.6 0.118 184.7)` | `#2a9d8f` | Secondary data series |
| `chart-3` | `oklch(0.398 0.07 227.4)` | `#264653` | Tertiary data series |
| `chart-4` | `oklch(0.828 0.189 84.4)` | `#e9c46a` | Quaternary data series |
| `chart-5` | `oklch(0.769 0.188 70.1)` | `#f4a261` | Quinary data series |

**Why these colors:** The palette is designed to remain distinguishable for users with common forms of color-vision deficiency (deuteranopia, protanopia). Colors are not overly saturated (professional tone) and remain legible against white backgrounds. Labels, legends, and other non-color cues are always retained alongside color (see §15.4) — color alone is never a required signal.

### 15.3 Chart Types and When to Use

| Chart Type | Use Case | AEGIS Context |
|------------|----------|---------------|
| **Bar chart** | Comparing categories | Grade distribution by subject, attendance by section |
| **Line chart** | Trends over time | Grade trends across quarters, attendance trends |
| **Pie/Donut chart** | Part-of-whole | Risk level distribution, attendance status breakdown |
| **Horizontal bar** | Long category labels | Subject performance comparison |
| **Stacked bar** | Composition over time | Attendance composition by month |
| **Area chart** | Volume over time | Assessment submission rates |

### 15.4 Chart Rules

- **Every chart has a title** (above or inside the chart).
- **Every chart has axis labels** (x and y axes).
- **Every chart has a legend** if more than one data series.
- **Data labels** on bars/points when there are < 10 data points.
- **Grid lines:** Horizontal only, `slate-200`, dashed.
- **No 3D charts.** Ever.
- **No exploding pie slices.**
- **Minimum bar width:** 24px.
- **No chart without a purpose.** Every chart answers a specific question.
- **Color is never the only differentiator.** Use patterns, labels, or different shapes if color alone distinguishes series.
- **Charts are responsive:** they resize with their container. On mobile, legends move below the chart.

### 15.5 Specific Chart Conventions

**Academic Performance:**
- Grades displayed as bar charts (one bar per subject or student).
- Y-axis: 0–100 scale (grades are percentage-based).
- Color: `chart-1` for current period, `chart-2` for previous period (if comparing).

**Attendance:**
- Stacked bar chart: present (green), late (yellow), absent (red) per time period.
- Y-axis: percentage or count.
- Time period: week, month, quarter.

**Risk Distribution:**
- Donut chart with three segments: low (green), moderate (yellow), high (red).
- Center text shows total student count.
- Labels always visible (not tooltip-only).

**Guidance Monitoring:**
- Line chart for an individual student's risk-level trend or risk-score trend, depending on the final data exposed by the approved backend/API contract.
- Bar chart for intervention completion rates.
- Table for active interventions with status badges.

## 16. Accessibility Baseline

### 16.1 Standard

**WCAG 2.1 Level AA** as the target compliance level.

### 16.2 Contrast Policy

Essential text, controls, and interface elements will use color combinations that meet the applicable contrast requirements. Decorative or disabled elements may use lower-contrast values where permitted.

| Element | Minimum Ratio | Notes |
|---------|--------------|-------|
| Normal text (< 18px) | 4.5:1 | Body text, labels, table content |
| Large text (≥ 18px or 14px bold) | 3:1 | Headings, KPI values |
| UI components & graphics | 3:1 | Borders, icons, focus indicators |

**Spot checks for the most common pairings (light mode):**

| Foreground | Background | Ratio | Notes |
|------------|-----------|-------|-------|
| `#27272A` on `#FFFFFF` | 14.9:1 | Primary text on surface — passes 4.5:1 |
| `#71717A` on `#FFFFFF` | 4.8:1 | Muted text on surface — passes 4.5:1 |
| `#71717A` on `#FAFAF9` | 4.6:1 | Muted text on page background — passes 4.5:1 |
| `#8B1E3F` on `#FFFFFF` | 8.9:1 | Maroon links/selected states on surface — passes |
| `#FFFFFF` on `#8B1E3F` | 8.9:1 | Text on primary buttons — passes |
| `#FFFFFF` on `#741832` | 10.9:1 | Text on primary hover — passes |
| `#FFFFFF` on `#0F172A` | 17.9:1 | Sidebar text on dark background — passes |
| `#741832` on `#FBE8EE` | 9.3:1 | Accent foreground on accent tint — passes |
| `#94a3b8` (`slate-400`) on `#FFFFFF` | 3.2:1 | **Decorative/disabled ONLY — never essential text** |

**Rule:** These spot checks cover the most common text and control pairings. They do not guarantee that every possible combination passes automatically. Each implemented combination must be verified during PH11.3 (axe-core scan + manual review). `slate-400` is never used for essential text; it is used only for disabled states and decorative elements.

### 16.3 Keyboard Navigation

- **All interactive elements** are focusable and operable via keyboard.
- **Visible focus indicator:** 2px `--ring` outline with 2px offset on all focusable elements.
- **Focus order:** follows DOM order (no `tabindex` > 0 except for specific widget patterns).
- **Skip navigation link:** first element in DOM, visible on focus ("Skip to main content").
- **Dialog focus trap:** when a modal is open, Tab cycles within the modal.
- **Escape key:** closes modals, dropdowns, and drawers.
- **Arrow keys:** navigate within menus, tabs, and select dropdowns.

### 16.4 Semantic HTML

- Use `<nav>` for navigation, `<main>` for main content, `<aside>` for sidebar.
- Use `<table>` with `<thead>`, `<tbody>`, `<th scope="col">` for data tables.
- Use `<h1>` through `<h6>` in hierarchical order (no skipping levels).
- Use `<form>` with `<label>` elements (not label-by-proxy).
- Use `role="alert"` for error messages and important notifications.
- Use `aria-live="polite"` for dynamic content updates (e.g., loading states, filtered results).

### 16.5 Form Accessibility

- Every input has a visible `<label>` (not placeholder-as-label).
- Required fields indicated with `*` and `aria-required="true"`.
- Error messages associated with inputs via `aria-describedby`.
- Error summary at top of form with links to each error field.
- Grouped fields use `<fieldset>` and `<legend>`.

### 16.6 Touch Targets

- Primary interactive controls should provide approximately 44px × 44px of usable touch area where practical.
- Buttons: minimum 32px height, but with padding to meet the ~44px touch area where practical.
- Navigation items: 36px height with sufficient padding for comfortable touch.
- Checkboxes and radio buttons: ~44px × 44px touch area (may be larger than visual size).

### 16.7 Screen Reader Support

- All images have `alt` text (decorative images: `alt=""`).
- Data tables have proper headers and scope.
- Dynamic content updates announced via `aria-live`.
- Icon-only buttons have `aria-label`.
- Loading states announced to screen readers.

### 16.8 Radix/shadcn Accessibility Note

Radix UI primitives provide accessible behavior (focus management, keyboard navigation, ARIA attributes) out of the box. However:

- **Radix is a foundation, not a guarantee.** Custom styling must not override accessible behavior.
- **Custom components** (non-Radix) must implement accessibility manually.
- **Testing is required.** Automated testing with axe-core + manual keyboard testing.

## 19. Design Decisions and Rationale

### 19.1 Typography Decision

**Decision:** Inter as the primary font family.

**Reason:**
- Designed for screens at the sizes AEGIS uses most (12–16px).
- Excellent legibility in dense tables and data views.
- Full Filipino/Tagalog diacritical support.
- Free, open source, widely supported.
- Tabular figures for aligned numbers.

**Alternatives considered:**

| Alternative | Why Rejected |
|------------|-------------|
| System font stack only | Less consistent cross-browser; smaller x-height at small sizes |
| IBM Plex Sans | Good but Inter has better community adoption and slightly better small-size rendering |
| Source Sans Pro | Older design; Inter is its successor |
| Roboto | Too strongly associated with Android/Google; less neutral |
| Noto Sans | Good fallback but Inter has tighter metrics for dashboard density |

**Impact:** Single font file loaded (Inter, variable weight). Minimal performance impact. Consistent rendering across Chrome, Firefox, Edge (NFR-014).

---

### 19.2 Color Palette Decision

**Decision:** Warm neutral surfaces with a warm maroon brand accent, supported by a soft rose accent family.

**Reason:**
- AEGIS serves a high school — students, parents, faculty, guidance, and administrators. Warm maroon reads as trustworthy and school-appropriate (school crests, uniforms) while remaining warm and approachable.
- The maroon `#8B1E3F` is softened for a student-friendly treatment — not overly dark, aggressive, or visually heavy.
- Rose-family accents differentiate roles without creating five unrelated color systems.
- Status colors (success/warning/destructive/info) follow universal conventions and remain separate from the brand color.
- Brand maroon is reserved for branding, primary actions, active navigation, selected states, and major interface accents. Stronger red remains reserved for errors, destructive actions, and critical states.
- OKLCH color space provides perceptually uniform colors for accessibility.

**Alternatives considered:**

| Alternative | Why Rejected |
|------------|-------------|
| Blue brand | Professional but impersonal/corporate — does not feel warm or friendly for younger students |
| Multi-color brand palette (per-role) | Five role-specific color systems fragment the interface; increases design debt |
| Dark/heavy maroon | Too visually heavy and aggressive; not friendly for younger students |
| Amber/orange brand | Too casual for an institutional dashboard |
| Green brand | Conflicts with success/positive status color |
| Purple brand | Too distinctive; distracts from data |

**Impact:** One brand color family (warm maroon/rose) plus a universal semantic system. One set of primary shades to manage, and role identity is conveyed subtly without fragmenting the interface.

---

### 19.3 Dark Mode Decision

**Decision: Light mode only for v1.**

**Reason:**

| Factor | Assessment |
|--------|-----------|
| **Development scope** | Dark mode doubles the CSS variable surface area and requires testing every component in both modes. This significantly increases PH11 scope for a student capstone project. |
| **Prototype coverage** | The approved prototype shows only light-mode designs. No dark-mode wireframes exist. |
| **User context** | AEGIS is used in a school setting (high school). Typical usage is during school hours on school-provided or personal devices in well-lit environments. Dark mode is not a primary need. |
| **Accessibility** | Light mode with proper contrast ratios (spot-checked in §16.2) targets WCAG 2.1 AA. Dark mode does not inherently improve accessibility. |
| **Maintenance** | Every new component must be tested in both modes. For a single-developer project, this is a significant ongoing cost. |
| **shadcn/ui support** | The CSS variable architecture is dark-mode-ready. Adding dark mode later requires only defining a `.dark` class override — no component changes needed. |
| **Token system** | The token system is designed to support dark mode in the future. Semantic tokens (§18.3) are structured so a `.dark` class can override all values without touching component code. |

**Future path:** If dark mode is needed post-capstone, the token system supports it. The `.dark` class approach (as shown in §18.3) can be added by defining a `.dark` selector with inverted semantic tokens. No component refactoring required.

**Alternatives considered:**

| Alternative | Why Rejected |
|------------|-------------|
| Light + dark from start | Doubles testing surface, no prototype reference, exceeds capstone scope |
| Dark mode only | Conflicts with prototype; worse readability in bright school environments |
| System preference detection | Premature without dark mode implementation |

**Impact:** Significant scope reduction for PH11. Components only need to be built and tested in one mode. The token architecture remains dark-mode-ready for future extension.

---

### 19.4 Spacing Decision

**Decision:** The spacing system is primarily based on a 4px scale, with limited smaller values (2px, 6px) for tight spacing.

**Reason:**
- The 4px grid is the industry standard for digital interfaces.
- Provides enough granularity without excessive tokens.
- Compatible with Tailwind CSS 4's spacing system (which is 4px-based by default).
- A few smaller values (2px, 6px) are needed for icon-to-text gaps and tight component padding.
- Sufficient for all AEGIS contexts: tables, forms, dashboards, sidebar.

**Alternatives considered:**

| Alternative | Why Rejected |
|------------|-------------|
| 8px base grid | Too coarse for tight spaces (table cell padding, form labels) |
| 5px base grid | Non-standard; creates alignment issues with rem-based sizing |
| Arbitrary spacing | Token-less approach leads to inconsistency across components |

**Impact:** Nearly all spacing in the application derives from this scale. No `margin: 13px` or `padding: 7px` values exist in the codebase.

---

### 19.5 Breakpoint Decision

**Decision:** Standard Tailwind breakpoints (sm: 640px, md: 768px, lg: 1024px, xl: 1280px, 2xl: 1536px).

**Reason:**
- These are Tailwind CSS 4's defaults — no custom configuration needed.
- They align with common device widths in the target range (320px–1920px per NFR-015).
- Well-tested across the industry.

**Alternatives considered:**

| Alternative | Why Rejected |
|------------|-------------|
| Custom breakpoints | No benefit over Tailwind defaults for this use case |
| Mobile-first only (single breakpoint) | Insufficient for desktop dashboard layouts |
| Container queries only | Not universally supported; sidebar layout needs viewport breakpoints |

**Impact:** Standard Tailwind responsive prefixes (`sm:`, `md:`, `lg:`, `xl:`, `2xl:`) work without custom configuration.

---

### 19.6 Component System Decision

**Decision:** shadcn/ui (Radix primitives + Tailwind styling) as the component foundation.

**Reason:**
- A confirmed carry-over from the PH11.1 technology stack — not re-decided here.
- Radix provides accessible primitives (focus management, keyboard navigation, ARIA).
- shadcn/ui copies component source into the project — no external dependency at runtime.
- CSS variable theming aligns with the token system designed here.
- Components are customizable via Tailwind classes — no CSS-in-JS overhead.

**Alternatives considered:**

| Alternative | Why Rejected |
|------------|-------------|
| Material UI (MUI) | Opinionated design language conflicts with AEGIS visual direction; heavy bundle |
| Ant Design | Enterprise aesthetic; less customizable; larger bundle |
| Chakra UI | Less mature Radix integration; CSS-in-JS runtime |
| Headless UI | Fewer components than Radix; less shadcn ecosystem support |
| Custom components from scratch | Radix already solves accessibility; rebuilding is wasteful |

**Impact:** Components installed via shadcn CLI. Source code lives in `src/components/ui/`. Customizable without fighting an external library's opinions.

---

### 19.7 Density Decision

**Decision:** Three density modes (compact, default, comfortable) available as context-driven presets, not user-togglable.

**Reason:**
- Different contexts genuinely need different densities (attendance recording needs compact; dashboards need comfortable).
- Making density a user preference adds UI complexity and testing surface.
- Context-driven density is simpler to implement and test.

**Alternatives considered:**

| Alternative | Why Rejected |
|------------|-------------|
| Single density for all | Too rigid; tables need to be denser than dashboards |
| User-toggleable density | Adds preference management UI; testing three modes for every component |
| Auto-density based on screen size | Unreliable; a 1024px screen could be a large tablet or small laptop |

**Impact:** Each component context defines its density. Tables default to compact/comfortable based on the parent page. Forms use standard density. Dashboards use comfortable.

---

### 19.8 Accessibility Baseline Decision

**Decision:** WCAG 2.1 AA as the target.

**Reason:**
- Required by good practice for educational software.
- WCAG AAA is too strict for a student project (contrast ratios like 7:1 are difficult with colorful status indicators).
- WCAG A alone is insufficient for an application used daily by students, parents, and staff.
- AA is the industry standard for government and educational software.

**Alternatives considered:**

| Alternative | Why Rejected |
|------------|-------------|
| WCAG AAA | 7:1 contrast ratio too restrictive for status colors and interactive elements |
| WCAG A only | Insufficient for educational context; many AA criteria are essential for usability |
| No formal standard | Unacceptable for an educational institution application |

**Impact:** Essential text, controls, and interface elements will use color combinations that meet the applicable contrast requirements; decorative or disabled elements may use lower-contrast values where permitted. Focus indicators on all interactive elements. Semantic HTML required. Screen reader testing included in QA.
