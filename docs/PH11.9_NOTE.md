## 2. Three security defects found and fixed

All three were found by **probing the live API**, not by reading code and
assuming. Each records its own measured before/after in the commit message.

### 2.1 Administrator authority was split between `is_staff` and `role`

`UserListView`, `UserDetailView` and `UserCreateView` gated on DRF's stock
`IsAdminUser`, which tests `is_staff`. Every other administrator area gates on
`core.permissions.IsAdminUser`, which tests `role == "admin"` (NFR-011).

These are not equivalent. `provision_qa_accounts` creates every QA account
through `create_user`, and `UserManager.create_user` defaults `is_staff` to
`False`. Verified against the live development database:

```
guidance  role=guidance  is_staff=False  is_superuser=False
admin     role=admin     is_staff=False  is_superuser=False   <- the QA administrator
faculty   role=faculty   is_staff=False
student   role=student   is_staff=False
parent    role=parent    is_staff=False
```

Measured before the fix:

```
admin.qa (role=admin, is_staff=False) -> GET /accounts/users/  403
core.permissions.IsAdminUser(admin.qa)                       True
```

The QA administrator held `role="admin"` and was refused by the endpoints it
administers. Fixed by moving the three views onto the project permission class.
`is_staff` is untouched and keeps its one real purpose: gating the Django admin
site. Only those three views changed — the other admin gates are already
role-based and were left alone.

11 regression tests (`AdminRoleAuthorityTest`) cover a role-only admin, an
`is_staff`-only impostor, an `is_superuser`-only impostor, `create_superuser`
(the shape the SEC-001 tests use), every non-admin role on list and create,
anonymous, agreement with the role gate the other admin areas use, and
deactivated admins rejected by the authentication layer.

### 2.2 Parents and students could write guidance records

`ConsultationRecordViewSet` and `RiskAlertViewSet` gated only
`create`/`update`/`partial_update` on the counselor role and fell through to
`IsAuthenticated` for everything else. `destroy` was therefore open to any
authenticated user whose queryset contained the row, and the
`acknowledge`/`escalate`/`resolve` actions were open too — they mutate status.

Measured before the fix:

```
                       parent  student  faculty  guidance  admin
DELETE consultation   204      204      404       404    404
POST acknowledge      200      200      404       200    404
POST escalate         200      200      404       200    404
POST resolve          200      200      404       200    404
DELETE risk-alert     204      204      404       404    404
```

A parent could delete their own child's counseling record and drive that child's
risk alert through the guidance workflow. Both viewsets now name every mutating
verb in `WRITE_ACTIONS` and gate it on `IsGuidanceUser`:

```
                       parent  student  faculty  guidance  admin
DELETE consultation   403      403      403       204    403
POST acknowledge      403      403      403       200    403
POST escalate         403      403      403       200    403
POST resolve          403      403      403       200    403
DELETE risk-alert     403      403      403       204    403
```

Counselor capabilities are unchanged. Parent and student read access is
unchanged, including the 404 an unlinked child produces. 20 regression tests.

### 2.3 Parents could read the assessment answer key

`AssessmentQuestionSerializer.to_representation` removed `correct_answer` only
for `role == 'student'`. A parent is served a published assessment through the
same nested `questions` field, so it returned the answer key:

```
                    before            after
guidance   correct_answer=['A']   correct_answer=['A']
student    correct_answer=[none]  correct_answer=[none]
parent     correct_answer=['A']   correct_answer=[none]   <- the defect
admin      correct_answer=['A']   correct_answer=['A']
```

Redaction is now keyed on the **caller** rather than on the published flag: the
key is present only for `assessment.created_by` and for admins. This is not a
published-only rule — a draft also withholds the key from a non-author, because
drafting is the author's own workflow. Only the key is removed; a parent still
receives `question_text`, `question_type` and `options`. 10 regression tests.

## 3. Recharts was not installed

`package.json` has no charting dependency, and none is needed.

The admin analytics endpoints return three scalars (`total_students`,
`overall_grade_average`, `grade_levels`), four risk counts, one average per
grade level, and one aggregate per section. Recharts would add a large
dependency to produce a chart of numbers that read correctly as formatted text,
against an already-large bundle.

**This is a judgement call, and it is reversible.** If the panel wants a trend
chart over terms, the data for one already exists at
`/analytics/subjects/trends/` (`subject_trends`, one average per subject per
grading period). Adding the library then would be a contained change. Nothing in
this phase blocks that.

## 4. Parent role

Three routes, all parent-only. Every list each page calls is already scoped
server-side to `ParentStudentLink` children, so selecting a child client-side
cannot reach another family's data — the picker can only offer children the
database returned to this caller.

| Route | Contents |
|---|---|
| `/app/parent/academics` | finalized grades, grade search, attendance totals, day-by-day record |
| `/app/parent/assessments` | published assessments with questions, and the selected child's results |
| `/app/parent/support` | read-only risk alerts, counselling sessions, behavioural notes |

### 4.1 Child resolution uses an existing contract

There is no "my children" endpoint, and none was invented. `ParentStudentLink`
is a real model but no viewset exposes it. `EnrollmentViewSet.get_queryset()`
already scopes a parent to `student_id__in=_get_linked_student_ids(user)` — the
same predicate the guidance and attendance viewsets use. Reading
`/academics/enrollments/` is therefore not "scanning arbitrary student records":
the server decides which rows exist.

### 4.2 Response envelopes genuinely differ

| Endpoint | Shape |
|---|---|
| `GET /attendance/records/` | `{count, results}` (paginated) |
| `GET /attendance/summary/` | **bare array** — `Response(results)` |
| `GET /analytics/students/{id}/metrics/` | `{status, data}` |
| `GET /assessments/assessments/` | `{count, results}` |

Handled separately rather than through one list helper.

`summary` is wired as a view-level action at `/attendance/summary/`, so the
student is a **query parameter**. Confirmed against the URL conf:
`/attendance/summary/<uuid>` raises `Resolver404`; `/attendance/summary/?student=<uuid>`
returns 200. This is a real trap in the existing `student/api.ts`, where the
template literal happens to produce the correct URL but reads as though it
appends a path segment.

### 4.3 Assessment list and detail differ

`AssessmentViewSet.get_serializer_class()` returns `AssessmentListSerializer`
for `list` (`question_count`, no nested questions) and `AssessmentSerializer` for
`retrieve`. Separate frontend types, so a list row cannot be read as if it had
questions.

An assessment may target a whole **section** and the view has no `?student=`
filter, so an assessment cannot be attributed to one child from the list
payload. The list is presented across the parent's children; the detail supplies
real targeting. Results *are* attributable, because
`AssessmentResultListSerializer` carries `student`.

### 4.4 Guidance is read-only by construction

The backend answers 403 for a parent on every mutating verb
([§2.2](#22-parents-and-students-could-write-guidance-records)), so no mutation
hook is defined and no control is rendered. A route test asserts the **absence**
of that vocabulary rather than a 403 round-trip, because with a mocked client
every write would appear to succeed.

Parent labels live in `features/parent/labels.ts` rather than being imported
from the guidance module: importing it would pull the counselor's mutation hooks
into a read-only parent bundle.

### 4.5 QA seed data

`parent.qa` had three linked children but **none** carried a risk alert, a
consultation or a behavioural note, so all three support tables rendered empty —
indistinguishable from a broken queryset.

Added, all deterministic and keyed on existing natural keys so a re-run reuses
the rows:

- one `RiskAlert` per child, spanning `under_monitoring`/`active`/`resolved` and
  `low`/`moderate`/`high`
- one `ConsultationRecord` per child, three session types, both visible statuses
- one `BehavioralNote` per child, one of each note type
- the wellness assessment result extended to the second parent child

No `Intervention` is seeded for these students: `InterventionViewSet` is
guidance-only and has no parent branch, so a plan would be invisible to the
parent while implying a surface they lack. The third child is excluded from the
wellness result because that assessment targets Grade 8 Bonifacio only, and a
result from an untargeted student would contradict the rule
`AssessmentResultViewSet.perform_create` enforces on real submission.

**Nothing fabricates model output.** `RiskScore` remains unseeded, the new alerts
use `source="manual"` and `risk_score_ref=None` exactly as
`POST /api/v1/guidance/risk-alerts/` produces them, and a test asserts the seed
still holds zero `RiskScore` rows and no parent-facing alert carries a score
reference.

## 5. Admin role

Eight routes replace a placeholder tree. PH11.7's admin `users` and `settings`
entries were **planned items pointing at routes that did not exist**, and
`academics` linked to a page describing shipped functionality as future work.

| Route | Contents |
|---|---|
| `/app/admin/academics` | academic year, grade levels, sections, subjects, subject assignments, grading periods, enrollments |
| `/app/admin/grades` | grade oversight plus the `finalize` action |
| `/app/admin/attendance` | read-only oversight with totals and per-student rows |
| `/app/admin/analytics` | school-wide and section-level aggregates |
| `/app/admin/users` | account list plus the create form |
| `/app/admin/data` | imports with per-row results, controlled exports |
| `/app/admin/cms` | announcements and resources through the CMS proxy |
| `/app/admin/audit` | the audit trail with bounded filters |

### 5.1 Where admin can write, and where it cannot

| Area | Admin write? | Why |
|---|---|---|
| Academic structure | **yes** | all viewsets use `IsAdminOrReadOnly` |
| Enrollments | **yes** | same |
| Grades | `finalize` **only** | `get_permissions` grants `finalize` to `IsAdminUser`; `encode`/`batch_import` are `IsFacultyUser` |
| Attendance | **no** | every write verb is gated on `IsFacultyUser` |
| Users | create **only** | no update/deactivate/delete/role-reset route exists |
| CMS | **no** | content is authored in Strapi; the proxy has no write endpoint |
| Audit | **no, by design** | `http_method_names` maps no write route |

Each restricted screen states its boundary in visible copy rather than hiding
controls, so a tester can distinguish "this role cannot" from "this screen is
unfinished".

### 5.2 NFR-010: admin analytics stay aggregated

NFR-010 requires administrators to view student data in aggregated or anonymised
form unless explicit consent is given.

The PH11.7 `AdminDashboard` carried a **"Low-Performance Students"** card calling
`/analytics/low-performance/`, which returns `student_id` and `student_name` —
named individuals. **That card was removed.** The endpoint itself is unchanged
and **no admin screen calls it**. Presenting those names on an admin dashboard is
what NFR-010 rules out, so the card is gone rather than relabelled.

No student-level admin table was built. Section performance is offered because
it is genuinely an aggregate per section.

### 5.3 Three placeholders deleted rather than kept

- **`settings`** — there is no `SystemSetting` model, view or route anywhere in
  the backend. The only mention is a comment in `apps/attendance/views.py`
  saying the absence threshold "will be replaced by SystemSetting lookup when CMS
  module is built (Phase 7)", and that never happened.
- **`users`** — became the real `admin/users` page.
- **`ATTENDANCE_PLANNED`** — parent and admin reached real attendance views;
  guidance gets no entry rather than one pointing at nothing.

`reports` stays planned for every role: no report contract exists. The only
related endpoints are administrator CSV/XLSX downloads.

## 6. Permissions audit — what was verified

Three distinct layers exist and are **not** interchangeable:

| Layer | Example |
|---|---|
| **Role** | `IsGuidanceUser`, `IsAdminUser` on a viewset |
| **Queryset scope** | `EnrollmentViewSet.get_queryset()` filtering a parent to linked children |
| **Object-level** | `CanViewAssessmentResult`, `IsParentOfStudent` |

Object-level authorization is **not** absent globally:
`AssessmentResultViewSet` applies `CanViewAssessmentResult` at the object level
*and* scopes the queryset, so there are genuinely two independent layers on
that resource. `core.permissions` also defines `IsParentOfStudent`,
`IsStudentOwnData` and `IsFacultyOwnerOfAssignment`, though the latter two are
imported without being wired to a viewset.

Verified intact, by probing rather than reading:

| Check | Result |
|---|---|
| Parent cannot access an unlinked student | 403 on metrics; 404 on guidance detail |
| Parent cannot mutate guidance | fixed in [§2.2](#22-parents-and-students-could-write-guidance-records) |
| Student cannot access admin routes | 403 across the board |
| Faculty cannot access admin-only operations | 403 |
| Admin access internally consistent | fixed in [§2.1](#21-administrator-authority-was-split-between-is_staff-and-role) |
| Notification recipient scoping | `NotificationViewSet.get_queryset()` filters `recipient=request.user`; preferences are `get_or_create(request.user)` |
| Account settings self-scoped | `CurrentUserView.get_object()` returns `request.user`; role/is_active/email are read-only (SEC-001) |

Measured row-count scoping across five roles on a 3-student fixture (parent
linked to 1):

```
endpoint      student  parent  faculty  guidance  admin
grades            1       1       3         3       3
enrollments       1       1       3         3       3
sections          1       1       2         2       2
subjects          2       2       2         2       2
subj-assign       1       1       2         2       2
attendance        1       1       3         3       3
att-summary       1       1       3         3       3
```

Parent saw exactly its linked child in every list and in the attendance summary.
`StudentMetricsView` returns 403 for a parent on an unlinked child and 200 for
guidance and admin.

### Frontend

```
npm test          -> 33 files, 535 tests passed   (4 consecutive clean runs)
npm run typecheck -> clean
npm run lint      -> clean
npm run format:check -> clean
npm run build     -> succeeds
```

Baseline was 32 files / 448 tests. Net **+1 file, +87 tests**.

### Test performance

The backend suite was unusable before this phase: PBKDF2-SHA256 at Django's
default 1,500,000 iterations, measured at **1.76 s per hash** on this machine,
with fixture users built in `setUp()` and so recreated per test method.

Measured on 21 guidance tests, stock hasher vs reduced:

```
before   157.649s
after      1.672s
```

Fixed by a test-only `PBKDF2PasswordHasher` subclass at 10,000 iterations.
`PBKDF2PasswordHasher` takes its iteration count as a constructor argument and
Django settings reference hashers only by dotted path, so the cost cannot be
lowered from settings alone. **The algorithm identifier stays `pbkdf2_sha256`**,
so the existing accounts test asserting a stored password begins with
`pbkdf2_sha256$` still passes and no test was weakened. `MD5PasswordHasher` was
rejected for exactly that reason — it would change the stored prefix to `md5$`.

`base.py`, `development.py` and `production.py` are **untouched** and keep the
full 1,500,000 iterations. No security test becomes vacuous: SEC-002 covers login
throttling, SEC-008 result immutability, and the password tests cover
verification, hashing, `must_change_password` and the validators.

The full suite now runs in ~26 minutes instead of exceeding two hours. The
remaining 25 slowest tests are all in `tests_qa_dataset`, each re-running the
full 100-student seed 2–3 times; that is inherent to what they verify.

### Pre-existing test flake fixed

`StudentProfilePage.test.tsx > shows the guidance-activity identity` failed in a
full-suite run and passed when the file ran alone. **Reproduced at the baseline
commit `b963612` before any of this phase's changes**: 3 failures in 4
full-suite runs, 0 in 4 single-file runs. The fuller admin suite only made it
reliable enough to notice.

Cause: the page cannot render its heading until `useGuidanceStudents` resolves,
and that query is gated behind five others (`enabled: !alertsQuery.isLoading &&
!consultationsQuery.isLoading && ...`). The assertion waits out **six sequential
resolution rounds** rather than one. Testing Library's default 1000 ms `findBy`
timeout is ample in isolation but not under parallel load.

Fixed by raising the wait budget to 5 s via a shared `findStudentHeading()`
helper. The heading and its name are still required exactly as before; no
assertion was weakened and no mock relaxed.

## 9. Known intentional limitations

Each is a deliberate choice against a real constraint, not an unfinished task.

1. **No system settings screen.** No `SystemSetting` model, view or route
   exists. Building one would require a backend model — out of scope for a
   frontend phase, and the requirement is not in the specification.

2. **No user update, deactivate, delete, role reassignment or password reset.**
   These are administrator operations a school would reasonably expect, and
   **no endpoint exists** for any of them. Role changes go through the Django
   admin site. The screen states this explicitly rather than rendering dead
   controls. `UserSerializer` additionally makes `role` and `is_active`
   read-only (SEC-001).

3. **No faculty picker on subject assignments.** No administrator-facing
   endpoint lists `FacultyProfile`s. `SubjectAssignmentSerializer.faculty` is
   required, so the form creates an **unassigned** assignment rather than
   offering a picker that cannot be populated. A teacher is attached through the
   Django admin site.

4. **No enrollment picker for unenrolled students.** No administrator endpoint
   lists student profiles. The picker offers only students already present in an
   enrollment, and the card says so when that set is empty.

5. **No CMS authoring.** Content is authored in Strapi.

6. **No schedule/timetable editor.** `ScheduleViewSet` is also
   `IsAdminOrReadOnly`, but the only server-side rule is start-before-end, so a
   form built here would offer almost no validation and no requirement asks for
   it.

7. **No reports screen, for any role.** No report contract exists; the only
   related endpoints are administrator file downloads.

8. **`guidance_records` import is parse-only.** It is an accepted `ImportType`
   and an admin may submit it, but `_dispatch_domain_processing` has no guidance
   importer and falls through to the legacy path, marking rows successful without
   writing any domain record. The form labels it as parse-only.

9. **Admin's `/app/assessments` is guidance-authored.** Admin reads the same
   endpoint guidance authors through, so the link is real, but the page's copy is
   written for a counselor. A distinct admin view was not built.

10. **Bundle advisory deferred.** `npm run build` emits the ~500 kB chunk warning
    at 900 kB. Performance optimisation belongs to a later phase; it was not
    addressed here.

## 10. Browser / deployment verification: UNVERIFIED

**No browser or live-deployment verification was performed.** This is stated
plainly rather than implied.

What was attempted, and what blocked it:

| Step | Result |
|---|---|
| Start the development backend | **succeeded** — `manage.py check` clean, server answered HTTP 401 on `/analytics/school-wide/` unauthenticated |
| Obtain QA credentials | **blocked** — `QA_SHARED_PASSWORD` is not set in this environment, and credentials must not be guessed |
| Log in as each of the five roles | **not performed** — no credentials |
| Verify seeded dataset through the API | **not possible** — see below |
| Drive the browser through the routes | **not performed** |

A further finding from the live database, reported as an observation rather than
a fix: the local development database is **not** the QA dataset. It contains 4
students, 4 enrollments, 4 grades, 9 attendance records, 2 risk alerts, 0
consultations, 0 behavioural notes, one unpublished assessment, **0 parent
links**, and three academic years including `DBG-2025` and `EX-2025`. The
E2E scratch data coexists with the seeded rows.

`parent.qa` therefore has **no linked children** in this database, so the parent
screens could not be exercised even with valid credentials. Running
`manage.py seed_qa_dataset` and `provision_qa_accounts` requires
`QA_SHARED_PASSWORD`, which is supplied by the Render service and is not
available here.

What this means for confidence:

- **Verified by execution:** all backend contracts, permissions and serializers,
  via 1,475 passing backend tests and by direct HTTP probing of a running
  server.
- **Verified by execution:** all frontend behaviour, via 535 passing tests
  including route guards, per-role navigation and role-redirect assertions.
- **NOT verified:** real rendering in a browser, real login with each QA
  account, and behaviour against the hosted DEV/QA deployment.

Before sign-off, a human should run the five QA logins against a seeded
environment and walk the routes in §4 and §5. The screens most worth a look are
the parent's child picker (three children, two sections), the read-only
support page (all three status families present), and the admin pages that
state a write boundary.
